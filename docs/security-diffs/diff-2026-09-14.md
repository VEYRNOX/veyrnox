### `src/pages/SendCrypto.jsx:330,578-614,1609,1951` — SAFE (adds I3 controls; closes a real gap)
**Commit:** `cc9efadb` fix(deniability): gate SendCrypto's shared-store reads and send writes (#2537), merged via PR #2559

**Change summary:** Adds
`deniable = isDecoy || isHidden || isDeniabilitySessionActive() || demoActive`.
All four shared-store `useQuery` calls now use `enabled: !deniable`:
`WhitelistedAddress`, `TransactionLimit`, `Transaction` and `AddressBook`. Their rows
are blanked locally, so a cached real-session result cannot render. Both post-broadcast
`Transaction.create` writes now run only when
`!deniable && !isDeniabilitySessionActive()`.

**Assessment:** This **ADDS** controls. Before this commit there was a live I3 gap on
`main`, and the 2026-09-13 report's scope did not include it. That report and its
addendum covered the seven `src/pages/` readers named in #2537, not `SendCrypto.jsx`.
The gap had three parts:
- **Writes.** An EVM or ERC-20 send from a decoy or hidden session wrote a row with the
  real txid, amount and addresses into the shared `veyrnox-appdata` store. The real
  session's history then showed that row.
- **Reads.** A decoy session read the real whitelist and the real spend limits. The
  whitelist surfaced in the address-poisoning label and as `whitelist_hit` in the
  advisor context.
- **A false comment.** A code comment said the whitelist query was already disabled in
  decoy/hidden sessions. It was not.

I read the diff and every remaining entity call in the file at `origin/main`: lines 578,
586, 596, 604, 1610 and 1952. No ungated `base44.entities.*` call is left. The file's
`trackEvent(SEND_COMPLETED)` calls at 1659/1973 are suppressed in deniability at the
`trackEvent.js` chokepoint.

Two design choices were checked:
- **Skip, not throw.** A throw after broadcast would report a failed send for funds
  that already left, and invite a second send. Skipping is the correct I4 reading here.
- **Bare `DEMO` is left out on purpose.** Blanking `TransactionLimit` for a real wallet
  in a build with a persisted demo flag would switch a real spend limit off. Here the
  fail-closed direction is to keep the limit.

Honest side effect, not a finding: a hidden or stealth session's own sends no longer
appear in that session's in-app history. That is the price of no per-session partition.
`sharedStorePages.deniability.test.js` gains 8 assertions (skip/fixme 0 → 0, none
removed), and the commit reports a 6-way mutation check. **I did not re-run the
mutations.** These are source-level pins. **Not device-verified.** The commit says so
too: the #2537 device check still stands and should now include a decoy EVM send.
#2537 remains OPEN.

### `src/lib/referralAttribution.js:64-93`, `src/components/ReferralHandoff.jsx`, `src/components/DeepLinkHandler.jsx:80`, `src/components/WalletEntry.jsx:1711` — SAFE
**Commits:** `f3f764a5` feat(referral): carry a referral code across a store install (#2541); `77c8f50d` fix(referral): lazy-load the install referrer plugin bridge

**Change summary:** This adds three ways to carry a referral code into a fresh install:
- **Android launch:** `captureInstallReferrer()` reads the Play Install Referrer.
- **Web entry screen:** a "Get it on Google Play" link that puts the code in `referrer=`,
  and "Copy code & get it on the App Store".
- **Native first run:** a "Have a referral code?" field with a Paste button that works
  only on tap.

All three paths store the code through the existing `captureReferralFromUrl`.

**Assessment:** I read both new files in full, plus `referralAttribution.js`,
`trackEvent.js` and `consent.js` at `origin/main`.
- **I3.** `ReferralHandoff` returns null when `isDeniabilityOrDemoActive()`.
  `captureInstallReferrer` checks the gate before its `await`, and
  `captureReferralFromUrl` checks it again afterwards (line 53). A session that switches
  during the referrer lookup cannot write. `WalletEntry` renders the handoff only in the
  `entry-tiles` view, which means no vault exists yet.
- **Input validation.** Every source normalises through `referralCodeFromUrl`, which
  enforces `CODE_RE` (`^VYX-[…]{6}$`). A referrer string Play hands back cannot store
  anything else. `playStoreReferralUrl` `encodeURIComponent`s the value.
- **I2.** `REFERRAL_CODE_APPLIED` goes through `trackEvent`. It returns before any egress
  unless `hasConsent()` is exactly `'granted'`. On a fresh install, whose consent is
  unanswered (`null`), a launch-time install-referrer capture therefore transmits
  nothing. The Play and App Store links are user-initiated navigations. The code in them
  is the inviter's public share code, not data about this user. `copyPlain`, not
  `copySecret`, is correct here because the value is not secret. The clipboard is read
  only inside the Paste handler, never on mount.
- **Native.** `InstallReferrerPlugin.java` sits only in the `gms` source set (google +
  samsung). `MainActivity` registers it reflectively inside
  `try/catch ClassNotFoundException`, so the huawei and fdroid flavours do not carry it.
  Every error path rejects, and the JS side treats a rejection as "no referrer", so
  launch is never blocked (I4). It adds no permissions beyond what Google's library
  merges for its binding.
- **Supply chain.** `com.android.installreferrer:installreferrer:2.2` is Google's
  single-purpose library, pinned to an exact version, and added only to the google and
  samsung configurations.
- **Panic residue.** The commit adds no storage keys. The Play referrer lasts as long as
  the install, so after a panic wipe the next launch can recapture the pending code.
  That state is identical to a fresh install from the same link, so it does not show
  that a wallet existed. It is not a tell.
