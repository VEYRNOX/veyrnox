### src/pages/SendCrypto.jsx:1788 — REGRESSION
**Commit:** `2ef3b12d` Add Digital Shield air-gap signing integration (#1930)
**Change summary:** `startSendAttempt()` branches on `useDigitalShieldMode`. The
non-Digital-Shield branch calls `sendTx.mutate()`, whose `mutationFn` runs
`evaluateSendGate()` (SendCrypto.jsx:1379). The Digital Shield branch returns
before that and calls `startDigitalShieldFlow` directly; the second stage,
`finalizeDigitalShieldSend()` (SendCrypto.jsx:1891), verifies the signed response
and broadcasts with no gate call at all.

**Assessment:** `evaluateSendGate` is the documented single chokepoint for the
send path (its own header enumerates checks 1–9). Bypassing it drops the
following, which the UI-level `confirmSendDisabled` flags do **not** replace:

- **2FA / step-up.** `twoFactorRequired: send2faMethod !== SEND_2FA.NONE`
  (SendCrypto.jsx:1390) is passed only inside the mutation. The Digital Shield
  path has no equivalent, so a configured Action Password / 2FA method is never
  demanded. The click-time `isSendReauthRequired()` check is a *freshness* check,
  not the 2FA gate.
- **Sign-time RASP re-evaluation.** The mutation re-derives `presignAtSign` from
  a **fresh** RASP artifact (SendCrypto.jsx:1281–1290) precisely because the
  render-time verdict can be stale. `blockedByRisk` (SendCrypto.jsx:1100) reads
  the render-time `presign`, so a RASP tier that degrades between render and sign
  is invisible on this path.
- **Sign-time spend-limit re-check.** `evaluateSendAgainstLimits` runs again
  inside the mutation (SendCrypto.jsx:1281). Limits are enforced on the *previous*
  step's Continue button (SendCrypto.jsx:2500), so the re-check that exists to
  catch state drift between steps is skipped.
- **`riskScoreFailed` fail-closed** and the new `txPolicy` PENDING branch.
- **The finalize/broadcast stage has no gate and no reauth-freshness check.** A
  user can prepare the QR, leave the screen idle past the reauth window, return,
  scan, and broadcast.

What *is* present, stated fairly: the confirm button is disabled on
`blockedByApproval || blockedByRisk || blockedByRaspBio || blockedByBtcRisk`;
`isSendReauthRequired()` is re-checked at click; and demo/deniability sessions
are rejected inside `startSendAttempt` (SendCrypto.jsx:1797). The response
verification in `digitalShield.js` is genuinely strong (see the SAFE entry
below). So this is a *partial* gate, not an absent one — but it is a second,
divergent copy of the gate expressed as UI state, which is the shape the project
has repeatedly recorded as the failure mode (WC H-1, PR #1276).

**Test coverage does not catch this.** `src/pages/__tests__/SendCrypto.digitalShield.test.js`
is a source-string regex guard: it asserts that identifiers are *present* in the
file (`expect(src).toMatch(/startSendAttempt/)`). No test asserts the Digital
Shield path reaches `evaluateSendGate`, and none would fail if it never did.

### src/api/tipScreen.js:236 — REGRESSION (I3)
**Commit:** `46c5faf0` Transaction intelligence and suspicious asset review (#1929)
**Change summary:** New exported `screenAssetContract()` posts
`{chain, from_address, to_address, contract_address, token_address}` to the TIP
proxy. Unlike its sibling `screenTransaction()` — which imports
`isDeniabilityOrDemoActive` (tipScreen.js:12) and falls back to the local IoC
cache as the *only* path in deniability — `screenAssetContract` carries no
deniability check.

**Assessment:** Its sole caller, `fetchRemoteContractIntel`
(`src/pages/SuspiciousAssets.jsx:110`), gates on
`contractIntelConfigured && contractIntelEnabled`, where
`contractIntelEnabled = hasContractIntelConsent()` reads the shared
`veyrnox-contract-intel-consent` key. That read is correctly ungated (reads leave
no trace, per the `lib/consent.js` precedent) — but it means **a decoy session
inherits the real user's `granted` answer**, and nothing downstream re-checks for
deniability. The call fires on row expansion (`SuspiciousAssets.jsx:152`,
`if (isOpen) fetchRemoteContractIntel(token)`), not behind a deliberate "screen
this" button, so merely opening a flagged token in a coerced session produces a
live outbound request.

I3 is "deniability mode → zero backend calls". This is a zero-to-one break on a
new path. The fix that matches existing structure is the guard in the egress
function, as `screenTransaction` already does — not a third call-site check.

Mitigating, and worth recording accurately: the payload is narrow (a zero
from-address from `ZERO_FROM_ADDRESS`, chain, contract) and carries no wallet
address, balance, or user-entered destination, so the leak is "this device asked
about contract X", not portfolio contents. The consent gate, the opt-in UI, the
6-hour cache, and the three new panic-residue keys are all correct work — the
single missing piece is the deniability check.

file. The web path (print container) is unchanged in substance from before.

### android/app/src/main/java/com/veyrnox/app/RaspIntegrityPlugin.kt:906 — NEEDS-REVIEW
**Commit:** `b8f01272` fix: harden Android integrity startup and smoke coverage (#1938)
**Change summary:** `isBlockTier()` is rewritten. It now returns `false`
unconditionally when `BuildConfig.DEBUG`, and in the non-debug branch logs
`android.util.Log.w("RASP", "BLOCK tier fired: hook=$hook tamper=$tamper

**Assessment:** Two separate issues in one hunk.

**(a) Detector attribution is logged to logcat in release builds.** Both `Log.w`
and the `getOrElse` `Log.e` sit inside the `else` (non-debug) branch, so they run

in isolation (debug builds are dev-only, and the release-cert guard in
