### `functions/api/buy/webhook.js:57-84,188` — SAFE (control ADDED)
**Commit:** `04c7cad0` fix(webhook): log signature prefixes, not the full HMAC, in warn mode (#2289)
**Change summary:** Adds `logSigPrefix()` and routes both `verify.header` and
`verify.expected` through it in the `verify_warn` log line, emitting
`<8 hex chars>…(len=N)` instead of the full digest.
**Assessment:** This closes the signing-oracle finding raised by the
2026-09-03 scan, and closes it at the right layer. `verify.expected` is
HMAC-SHA256(rawBody, `TRANSAK_WEBHOOK_SECRET`) over a body an unauthenticated
caller fully controls; `logSafe`'s `MAX_FIELD` is 64 and a SHA-256 hex digest is
exactly 64, so the previous line was never truncated. Verified in the new code
that `SIG_LOG_PREFIX = 8` is applied to *both* sides, not just the computed one —
a fix that trimmed only `computed=` would still leak nothing useful, but a fix
that trimmed only `header=` would have left the oracle intact.

The regression pin is real, not decorative:
`functions/api/buy/__tests__/webhook.test.js` computes the attacker-chosen
body's true signature, asserts the warn line contains neither the full digest
nor its first 24 characters, and asserts the 8-char prefix *is* present — so it
fails both on a re-widening and on an over-correction that removes the operator's
ability to compare. It also asserts `realSig` is 64 chars and differs from the
fixture, so the test cannot pass vacuously.

Correct severity for the original: the exploit needed log-read access, so it was
never an open door. The reason to fix it before the planned `warn`→`strict` flip
still holds — HMACs do not expire, so signatures harvested during a warn window
would survive the flip they exist to enable.

Gap 2 is the notable one because the script itself already documents why static
