### `src/pages/Subscription.jsx` — SAFE (new egress path, verified against both chokepoints)

**Commit:** same. +89 lines.

**Change summary:** Three changes. (1) A new `trackEvent(EVENT.PAYWALL_SHOWN,
{ trigger: 'plans_view' })` fired once on `/plans` mount. (2) Offering
resolution gains a third state — `'loading' | 'ready' | 'unavailable'`, tracked
separately per tier — so a rejected lookup and a resolved-but-empty offering are
distinguishable instead of both leaving the CTA reading "loading pricing"
forever. (3) The CTA becomes a retry button in the `unavailable` state, wired to
a `reloadKey` bump that re-runs the effect.

**Assessment — I2/I3 (the new egress).** This is a new outbound path and was
treated as one. It is correct, and correct in a way that is easy to get wrong in
the opposite direction:

- `paywall_shown` is not a new event type. It is already in `EVENT`, already in
  the client `ALLOWED_EVENTS` preflight, and — confirmed by reading
  `sql/telemetry-events-allowlist.sql:60` out of the ref — already in the SERVER
  allowlist since PR #1340, alongside `paywall_dismissed` and
  `paywall_converted`. No SQL change is implied. Only the `trigger` metadata
  value is new.
- The payload is `{ trigger: 'plans_view' }` — a fixed literal. It carries no
  holdings, address, asset, tier, deniability state or user-derived value.
- **The call site deliberately adds no consent or deniability guard, and that is
  right.** `src/api/trackEvent.js` was read in full from `origin/main`: it
  returns early on `DEMO || isDeniabilityOrDemoActive()`, then on a
  non-allowlisted event, then on a >4096-byte metadata payload, then on
  `!hasConsent()`, and only then mints a device id and calls
  `rpc('track_event', …)`. `CLAUDE.md` states the rule explicitly — gate at the
  single egress chokepoint, and *"do NOT re-guard at call sites — that
  three-place duplication is exactly how the third writer shipped unguarded."*
  A guard here would have been the finding.

**Assessment — I4 (does the new enabled state ever fire a purchase with no
package?).** No. The two conditions are complementary, and were checked as a
pair rather than read individually:

```
disabled: !selectedPackage && offeringsState !== "unavailable"
onClick:  !selectedPackage && offeringsState === "unavailable" ? retryOfferings : handleUpgrade
```

`!selectedPackage` + `loading` → disabled. `!selectedPackage` + `unavailable` →
enabled, but routed to `retryOfferings`. `selectedPackage` present →
`handleUpgrade`. There is no state in which a null package reaches
`handleUpgrade` on an enabled button. The AI CTA repeats the shape against
`aiPurchaseAvailable` / `aiOfferingsState`, and is consistent with itself. The
`OFFER_UNAVAILABLE` fail-closed contract in `purchases.js` is untouched —
nothing here creates a fall-through to a full-price charge.

effect's `cancelled` flag, which with the new `reloadKey` dependency would let a

context, and both `.catch` arms carry `if (!cancelled)` explicitly. Confirmed by
