### 2. `tip-chat` deployment drift — CONFIRMED, and wider than recorded

Production `tip-chat` (project `jwstkrtslotnjyerzzsi`) is version 38, last
updated **2026-08-23T18:18:15Z**. Two commits have touched
`supabase/functions/tip-chat/index.ts` since:

- `d8dc6e61` (2026-08-23T21:56:01Z) — about three hours after the deploy
- `038663df` (2026-09-16T17:38:03Z) — the #2587 entitlement hardening

So the deployed function has diverged from repo source for 26 days, not since
the 2026-09-16 commit. `CLAUDE.md` states as a hard rule that the deployed
version must match the repo source; it does not.

The deployed body was read, not inferred. The divergence is not a subset of
comments: **the deployed function contains no entitlement gate at all.** Repo
source declares `REQUIRED_ENTITLEMENT = 'ai_security_protection'`, resolves it
against RevenueCat with a bounded positive/negative cache, and returns
`403 entitlement_required` on two paths — a missing or malformed
`X-Rc-User-Id`, and an id without the active entitlement. None of that exists
in v38, which proceeds from the anon-key presence check straight to signing and
forwarding the request upstream.

The live effect is that the server-side tier gate for the paid AI advisor
exists only in source. What remains in force on production is the client's own
check (`advisorOnlineEnabled` in `SecurityAdvisor.jsx:1083`), which the client
controls, and whatever per-device cap the upstream TIP Worker applies — the
deployed function passes a `402` through unmodified, so upstream enforcement
plainly exists, but its strength was not examined and is outside this scan.

Rated NEEDS-REVIEW rather than REGRESSION, deliberately: no commit in this
window caused it, and the live endpoint was not exercised. The conclusion rests
on two artifacts that were read in full — the deployed function body and the
repo source — not on a request. Deploying `038663df` closes it; until then,
"#2587 hardened the entitlement lookup" describes source only and must not be
written as a live control.

## Method — what this pass actually did

This pass departed from static-only analysis in one respect, and the departure
is stated rather than buried: it issued read-only queries to the live Supabase
projects (`has_function_privilege` reads, an Edge Function listing, and one
Edge Function source read). Nothing was written, no migration applied, no
secret read, and no HTTP request made to `tip-chat`, the TIP Worker or any
wallet endpoint.

The reason is that both carried-forward items were phrased as questions only
live state can answer, and two consecutive reports had restated them without
answering either. A NEEDS-REVIEW that is copied forward unverified decays into
a claim about the present that nobody checked.

Nothing here is device-verified, dynamically tested, or independently audited,
and no on-chain confirmation is involved. This remains INTERNAL analysis.

Proposed addition for whoever maintains `SKILL.md` — this task may only write
its own report, so this is the handoff:

> **Step 3b — carried-forward items are re-verified, not re-stated.** When a
> report carries a NEEDS-REVIEW whose resolution depends on a deployment, a

> say that explicitly. Copying an unverified item forward turns a
> point-in-time observation into an unfalsifiable standing claim — `tip-chat`
> drifted for 26 days while two reports described it as a recent,
> single-commit gap.

This is the first run to hit the deployed-state gap, so it is a note, not an
escalation. If a second run hits it, the honest reading is that a scan scoped
to the repository cannot assess controls whose enforcement lives outside it.
