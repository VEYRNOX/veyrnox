### src/wallet-core/netUrl.js:104 + src/pages/NetworkManager.jsx:137,166 — NEEDS-REVIEW
**Commits:** `ff8709be` fix(network): K-2 gate NetworkConfig CRUD + surface rejected env overrides + reject URL fragments (#1827); `20b245a3` (round-4 `isWellKnownRpcHost` fix)
**Change summary:** `assertSafeRpcUrl` gained a `WELL_KNOWN_RPC_HOSTS` allowlist —
an https URL to any host outside the curated RPC/indexer list now throws unless
`VITE_ALLOW_CUSTOM_RPC=1` or `globalThis.__veyrnoxAllowCustomRpc === true`.
**Assessment:** The RPC-egress hardening itself is sound and fails closed. The
problem is the blast radius: `safeExternalUrl()` is a thin wrapper over
`assertSafeRpcUrl`, and its **only** consumers are block-explorer URLs in
`NetworkManager.jsx`. The allowlist contains RPC providers only — no explorers.
Concretely, every default network's `explorer_url` is now rejected:

| network | explorer_url | in allowlist? |
|---|---|---|
| Ethereum Mainnet | `https://etherscan.io` | no |
| BNB Smart Chain | `https://bscscan.com` | no |
| Polygon | `https://polygonscan.com` | no |
| Arbitrum One | `https://arbiscan.io` | no |
| Optimism | `https://optimistic.etherscan.io` | no |
| Avalanche C-Chain | `https://snowtrace.io` | no |
| Ethereum Sepolia | `https://sepolia.etherscan.io` | no |

So `NetworkManager.jsx:137` renders the Globe explorer link for **zero** of the
seven default networks, and `:166` rejects a user-entered explorer URL — including
the field's own placeholder, `https://etherscan.io` (`:158`). Fail-closed, so this
is a functional regression, not a vulnerability.

Worth noting how it got through: `netUrl.test.js:73` pins the coupling and reasons
about the caller in the future tense — *"If a future caller renders an arbitrary
explorer URL, gate at that render site — do NOT weaken the shared validator"*. That
caller already exists and predates the change. The advice is right; the tense is
wrong. Suggested fix follows the test's own instruction: a separate
`safeExplorerUrl()` (scheme/credential/fragment checks, no RPC-host allowlist) for
the render site, leaving `assertSafeRpcUrl` untouched.

### sql/api-security-hardening.sql:374 — NEEDS-REVIEW
**Commit:** `b9a9f7ec` fix(referral): collision-safe register + discount validation (#1779)
**Change summary:** `register_referral_code` changes return type `void` → `text`
and mints a fresh server-side code on collision instead of silently
`ON CONFLICT DO NOTHING`; `record_attribution` gains a discount bound
(`0 ≤ p_discount_cents ≤ p_revenue_cents`).
**Assessment:** Both fixes are correct — the silent-collision bug meant a client
displayed a code whose attributions accrued to a stranger, and the unbounded
discount let a caller report impossible commission. Two operational notes:

- **Ordering is load-bearing and unrecorded here.** `src/api/referralApi.js` now

  PR — recorded so it is not mistaken for hardened just because the neighbouring
  code was.

### src/rasp/attestation.js:216 — LOW (note, not a defect)
**Commit:** `13379d93` fix(rasp): session-scoped attestation-latch (#1838)
**Assessment:** Real fix for a real oracle — an attacker who could mute the
attestation leg after a genuine FAIL previously got the next presign downgraded
BLOCK → WARN. The latch now makes a muted probe inherit the fail. The commit
message says clearing it "requires the attacker to defeat the whole attestation
chain, not merely mute it" — true of the probe path, but the latch **also** clears
on `veyrnox:app-lock`, which `WalletProvider.lock()` dispatches on every lock path
including the idle timer. So "mute the attestation leg + wait for or trigger an
idle lock" also clears it. The reset is a deliberate trade (a rebooted-clean device
must not stay BLOCK-tiered forever) and is documented in the code; it is the
commit-message framing that overstates. Stated here so a later reader does not
inherit the stronger claim.
