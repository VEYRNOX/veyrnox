## ⚠️ REGRESSION DETECTED

1. **`ios/App/App/SceneDelegate.swift:67-73`: debug instrumentation marked "remove before commit" is on `main`.** It writes every incoming custom-scheme URL to the iOS unified log with `NSLog`, whether or not the URL passes the allowlist. A `veyrnox://wc?uri=wc:…` pairing link carries the WalletConnect `symKey`, so the pairing secret ends up in device logs, sysdiagnose bundles and Console.app. This breaks the A09 rule against logging sensitive data, and it runs in release builds. iOS 1.0.2 has **not** been submitted to Apple yet (`docs/RELEASE-v1.0.2.md:5`), so it can be removed before it ships.
2. **`ios/App/App/SceneDelegate.swift:42-56`: on cold launch, deep links skip the native allowlist.** When a URL or universal link launches the app, UIKit delivers it in `connectionOptions`, not through `scene(_:openURLContexts:)`. The code hands `connectionOptions` unfiltered to `Capacitor.SceneDelegateProxy`. That proxy then replays the URLs through its **own** `scene(_:openURLContexts:)` and `scene(_:continue:)` (`CAPSceneDelegateProxy.swift`), not through the filtered methods in this delegate. Before the UIScene migration, cold-launch URLs still reached `application(_:open:options:)`, where the allowlist ran. The JavaScript deep-link validation still applies, so this is one defence-in-depth layer lost, not the only control. It is still a control removed on one path.

### ios/App/App/SceneDelegate.swift:42-56 — REGRESSION (defence-in-depth)
**Commit:** d4af8d9d (#2751)
**Change summary:** `scene(_:willConnectTo:options:)` passes `connectionOptions` to `Capacitor.SceneDelegateProxy.shared.scene(…willConnectTo:…)` without filtering it.
**Assessment:** The proxy source was read from `node_modules/@capacitor/ios/Capacitor/Capacitor/CAPSceneDelegateProxy.swift`, version 8.5.0 in the shared checkout; the lockfile pins 8.5.2, which has not been diffed. On the first `capacitorViewDidAppear`, the proxy calls `self.scene(scene, openURLContexts: connectionOptions.urlContexts)` and `self.scene(scene, continue:)` on **itself**, and posts every URL to the plugins. So a URL or universal link that cold-launches the app never passes through `AppDelegate.isAllowedDeepLink`. Before the migration, the pre-scene AppDelegate filtered this path in `application(_:open:options:)` and `application(_:continue:)`. The file's own header says the native chokepoint exists to act "BEFORE the JS layer runs". On cold launch it no longer does.
**Suggested fix (not applied):** Filter `connectionOptions.urlContexts` and `connectionOptions.userActivities` in `willConnectTo`, or keep them away from the proxy and re-deliver them through this delegate's own filtered methods once the bridge is up. Add a source pin next to `deepLinkAssociations.referral.test.js`.

### src/pages/BuyCrypto.jsx:119-190 — NEEDS-REVIEW (deliberate, owner-ruled reduction)
**Commit:** ae50bfef fix(buy): don't relock the wallet during the Transak hand-off (#2756)
**Change summary:** The native Buy hand-off now wraps `Browser.open` in `withLockSuppressed`. The suppression ends on `browserFinished` or after a hard `BUY_LOCK_SUPPRESS_MAX_MS = 15 min`. If the timer cannot be armed, the window is never opened, and a failed `Browser.open` closes it.
**Assessment:** The change is documented in the code as an owner ruling from 2026-09-23 and states the lost protection plainly. Its I4 bound holds: every path to `finish()` was traced (timer, listener, listener-registration rejection, open failure), and a `settled` latch makes `finish()` idempotent. The four new tests cover each release path. From `src/wallet-core/keystore/native.js:334-339`, `_lockSuppressDepth` blocks only `fireLockHook()`, the background-lock path. Manual lock, idle auto-lock and panic wipe are unaffected.
The net effect: for up to 15 minutes, **backgrounding the app does not lock it**. That includes the user returning to the wallet and then leaving again for an unrelated reason before `browserFinished` fires, for example after a `/buy/return` universal link where the in-app browser may still be open. That is a real widening of the unlocked window on a stolen or handed-over phone, beyond what the three existing ~2s uses of this mechanism allow. It is recorded here as a residual, not as a defect. Two options to weigh: end suppression when `/buy/return` is handled, or when the app returns to the foreground, whichever comes first.
Per the standing memory note, this file is owner-only for changes. This is a report, not a proposed patch.

### src/pages/WalletAccessReset.jsx:614-622 — NEEDS-REVIEW (low)
**Commit:** d4af8d9d (#2751)
**Change summary:** Adds `maxLength={256}` to the recovery-flow **new vault password** field, and `maxLength={512}` to the seed textarea.
**Assessment:** The seed cap is fine: 24 words × the longest non-English word still fits comfortably. The password cap is the concern. `maxLength` **silently truncates** a paste, this field has no confirmation input (`recPw`, line 107; compare `confirmPw` for the change-password flow), and the unlock path in `WalletEntry.jsx` does not cap. A password-manager passphrase longer than 256 characters would be stored as its first 256 characters. The next full-length paste at unlock would then fail, and each failure counts toward the panic-wipe limit. The case is rare, but the failure is silent. For a credential being *created*, reject over-length input with a message rather than truncating it.
