### functions/api/buy/webhook.js — NEEDS-REVIEW
**Commit:** `3f3613b7` feat(buy): add Transak order-webhook receiver (log-only)
**Change summary:** New public Cloudflare Pages Function at
`/api/buy/webhook`, registered with Transak on 2026-08-31 for both prod and
staging. Receives ORDER_* lifecycle events, logs three fields, returns
`200 {ok:true}`.

**Assessment:** The file is unusually honest about its own limits — it states
in-comment that Transak's docs do not specify the signing scheme, that it
therefore performs **no cryptographic verification**, and that verification must
land before the data drives any user-visible action. That framing is correct and
I4-consistent: the handler has no side effect beyond `console.log`, so a spoofed
event cannot corrupt state, mint an entitlement, or touch attribution. Rated
NEEDS-REVIEW for the surface itself, not for a false claim.

Three things the in-file comment does not cover:

1. **Log injection.** `eventID`, `orderId` and `status` are taken straight from
   attacker-controlled JSON and interpolated into a single `console.log`
   template (`webhook.js:47`). Newlines are not stripped, so a caller can post
   `{"eventID":"X\n[buy/webhook] ref=deadbeef event=ORDER_COMPLETED order=…"}`
   and forge additional, well-formed-looking log lines. The file already names
   "a spoofed event misleads an operator reading logs" as the residual risk —
   forged *log lines* are the sharper version of exactly that risk, and are not
   mitigated by the log-only design.
2. **No length bound.** None of the three fields is truncated, so a single POST
   can write an arbitrarily large log record.
3. **No rate limit or auth of any kind.** Public, unauthenticated, and it 200s
   on every input including malformed bodies (deliberate — Transak retries on
   non-2xx). Combined with (2) this is a cheap log-flooding primitive.

None of these are exploitable into state change today. They matter at the moment
verification is added and this data starts driving attribution — the sequencing
the file itself asks for. Suggested minimum before that: strip `[\r\n]`, cap each
field (~64 chars), and verify before trusting.

Test coverage (`functions/api/buy/__tests__/webhook.test.js`, 4 cases) is
proportionate: ORDER_COMPLETED happy path, malformed body still 200, GET → 405,
missing `webhookData` → `UNKNOWN`/`null` without throwing. No test asserts
sanitisation, because none is implemented.

### android/app/src/huawei/java/com/veyrnox/app/HuaweiIapPlugin.kt — NEEDS-REVIEW
**Commit:** `2cc707e8` feat(android): wire Huawei AppGallery HMS IAP (huawei flavor only)
**Change summary:** New 362-line Capacitor plugin driving HMS IAP directly —
AppGallery has no RevenueCat backend. Handles product query, purchase,
restore, owned-purchase pagination and subscription management.

**Assessment:** **Purchase receipts are never signature-verified.** HMS returns
`inAppSignature` alongside `inAppPurchaseDataList` on `obtainOwnedPurchases`,
and `inAppDataSignature` alongside `inAppPurchaseData` on
`parsePurchaseResultInfoFromIntent`. Neither is read anywhere in the huawei
source set — `grep -i 'inAppSignature|signature|PublicKey|verify'` returns
nothing. Entitlement is granted purely from fields inside the unverified receipt
JSON:

```kotlin
if (!purchase.isSubValid || purchase.purchaseState != PurchaseState.PURCHASED) return@forEach
when (productId) {
  "safety_plus_monthly", "safety_plus_annual" -> active.put("safety_plus", …)
```

Both the fresh-purchase path (`:172`) and the restore/customer-info path
(`:246`) grant on the same unverified basis. On a device where HMS Core is
hooked or the IAP response is otherwise attacker-influenced, `safety_plus` and
`ai_security_protection` can be asserted without a purchase. Huawei's own
integration guidance treats signature verification (preferably server-side) as
required, not optional.

**Severity is bounded by two facts, and both should be stated rather than
assumed away:** (a) this grants a *paid subscription tier*, not wallet key
access, vault decryption, or signing authority — no I1–I5 invariant is
implicated; (b) the huawei flavor is not shipped. There is no huawei
release/publish job in any workflow (`grep -i huawei .github/workflows/*.yml`
matches no release, publish, upload, bundle or aab step), and the commit series
describes the adapters as scaffolding. So this is a gap to close before
AppGallery distribution, not a live exposure.

Secondary, same file — **product-ID drift, currently fail-closed.** The plugin
hardcodes the four product IDs as string literals, while the JS side
(`huaweiPurchases.js:20-30`) reads them from
`VITE_HUAWEI_*_PRODUCT_ID` with those same values only as fallbacks. Override
any of those env vars and JS will purchase a product the native mapping does not
recognise, so `customerInfoFromPurchases` silently maps nothing and the
entitlement is never granted. It fails in the safe direction, but it fails
silently and the two sources of truth should be one.
