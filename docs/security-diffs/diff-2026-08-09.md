### src/api/tipScreen.js:76 + src/lib/localIocCache.js:57 — NEEDS-REVIEW
**Commit:** `965379e1` feat(advisor): local IOC cache — signed manifest sync for offline + deniability screening (#1624)
**Change summary:** `screenTransaction` now calls `tryLocalScreen()` — which calls
`hydrateFromCache()` → `idbGet()` → `openDb()` — BEFORE the `if (inDeniability) return
null` early exit. Previously `isDeniabilityOrDemoActive()` was the first line of the
function and returned immediately.
**Assessment:** `openDb()` is `indexedDB.open('veyrnox-ioc-cache', 1)` with an
`onupgradeneeded` that creates the object store. `indexedDB.open` **creates the database
if it does not exist** — so the first screening call inside a decoy, duress or demo
session writes a new (empty) IndexedDB database to disk. The module's own header states
"Deniability sessions read from cache only", and `tryLocalScreen`'s comment says
"hydrateFromCache reads IndexedDB, never the network" — true about egress, not true about
persistence.

No network call is made and no data is written into the store, so I3's egress clause holds
and the tell is weak (a decoy session is *meant* to look like a real wallet, and a real
wallet legitimately has this DB). The reason to raise it anyway is the precedent this repo
has already set twice: `panic.js`'s own new comment in this same window says the
threat-intel DB's "PRESENCE is a tell that this device has done screening", and
`METADATA_RESIDUE_KEYS` exists because `veyrnox-first-run-tour-seen` (DIFF-0728) and
`veyrnox-device-id` (DIFF-0723) were judged tells on presence alone. The specific bad
sequence is: panic wipe erases the DB (correctly — `eraseIocCacheDatabase()` was added in
this same PR), the coercer then drives the decoy wallet, and the DB is recreated
post-wipe by a session that is supposed to leave no trace.

Reachability: `SecurityAdvisor.jsx:499` unconditionally, and `SendCrypto.jsx:709` when the
shared `remoteScreen` opt-in is on. Both are reachable in a decoy session by design —
delivering screening to decoy sessions is the stated point of the change.

Suggested shape: have `hydrateFromCache()` open the DB read-only-if-exists (probe via
`indexedDB.databases()` where available, or gate the create on a non-deniability caller),
and add `veyrnox-ioc-cache` to whatever post-wipe inspection asserts `clean`.

### src/lib/localIocCache.js:186 — NEEDS-REVIEW
**Commit:** `965379e1` feat(advisor): local IOC cache (#1624)
**Change summary:** `refreshManifest()` verifies an Ed25519 signature over
`canonicalStringify(body.payload)` and accepts any manifest that verifies.
**Assessment:** Signature verification itself is correct and fails closed — missing
signature, wrong `public_key_id`, or a failed `crypto.subtle.verify` each throw, and
`hydrateFromCache()` re-verifies the stored copy on load, which defends the on-disk row.
Two gaps in what the signature is allowed to authorise:

1. **No rollback protection.** `payload.generated_at` is parsed into `_memoryMeta` and
   never compared against the stored manifest's. Any *validly signed* older manifest is
   accepted and overwrites the newer one — no monotonic check, and no rejection on
   `generated_at` far in the past. An attacker able to serve a stale-but-authentic
   response (network position, a cache/CDN layer, a captive network) can roll screening
   back to before a given address was listed. Impact is bounded in normal mode, where a
   local miss still falls through to the live TIP call — but in deniability and offline
   mode the local cache is the **only** path (`tipScreen.js`: `if (inDeniability) return
   null` after the local check), so a rollback there is a silent, total screening blind
   spot in precisely the coercion scenario the feature was added to cover. A
   `generated_at > stored.generated_at` check inside the verify branch closes it.

2. **No response size cap.** `resp.json()` is called on an unbounded body, then the whole
   payload is put into IndexedDB and expanded into a `Map`. CLAUDE.md's API rules require
   every endpoint to enforce a payload cap; this one is a client consuming our own
   server, but the manifest is the one input the wallet accepts wholesale.

Also noted, not a finding: `canonicalStringify` must stay byte-identical to the server's.
The author flags this; there is no test pinning the two implementations together, so drift
would present as a silent verification failure (fail-closed, so safe, but silent).

### src/wallet-core/keystore/native.js:1047 — NEEDS-REVIEW (low)
**Commit:** `b27ec1bb` feat(wallet-core): wire dekCache into unlock hot path — Personal Backup phase 1b (#1644)
**Change summary:** Six paths now manage the `vault_dek_v1` cache slot: `_unlockInner`
populates it, and `upgradeKekToV3`, `changePassword` (both branches), `unenrollKek` and
`clearVault` clear it. `enrollKek` does not.
**Assessment:** `enrollKek` is the one remaining path that mints a fresh DEK
(`randomDek()`, line 1080) and writes a new vault without calling `clearDekCache()`. It is
not exploitable today, and the reason is worth stating precisely because it is
incidental rather than designed: `enrollKek` generates a fresh 32-byte `saltBytes`, so the
new KEK cannot unwrap a pre-existing cache blob, the read misses, and `_unlockInner` falls
back to `unwrapDek` and overwrites the blob. Safety rests on salt freshness, not on the
cache being cleared.

Why it still matters: the failure mode if that ever stops holding is a **permanent
lockout with the correct PIN**. If any future path produces the same KEK over a different
DEK, `tryReadDekCache` succeeds, `unwrapDek` is skipped, and `decryptVaultWithDek(blob,
dek)` throws — and the fallback covers only cache *unwrap* failure, not a cache that
unwraps cleanly to the wrong DEK. There is no "retry the primary wrap after a failed
decrypt" path and nothing clears the cache on that error, so every subsequent unlock
repeats it. Adding `clearDekCache()` to `enrollKek` makes the invariant "every
DEK-rotating write clears the cache" true without exception; alternatively, catch the
`decryptVaultWithDek` failure on the cache path, clear the cache, and retry via
`unwrapDek` once.

The rest of the DEK-cache work is sound. `dekCache.js` uses a distinct AAD
(`veyrnox/kek/dek-cache/v1/aad`) so a cache blob cannot be unwrapped as a vault blob;
unwrap failures are generic (no cross-AAD oracle); the cache requires the full KEK, so
neither the hardware factor nor the PIN is bypassed and the biometric prompt still runs;
`clearVault()` clears the slot and `WalletProvider.panicWipe` calls `clearVault()`, so
panic wipe covers it.

### 1. The recorded verification timestamp was wrong by one hour

That section reads "Verified against `origin/main` at `942b7e28` (2026-08-09 10:02 UTC)".
The real time was **09:02 UTC**. PowerShell's `Get-Date -Format "u"` renders **local**
time and appends a `Z`-style suffix — it does not convert to UTC. The machine was on
BST (UTC+1), so every timestamp taken that way reads an hour late. Confirmed by
comparison: `Get-Date -Format "u"` returned `2026-08-09 10:23:30Z` while `date -u` in the
same minute returned `2026-08-09T09:24:00Z`, and GitHub's own `mergedAt` for PR #1653 is
`2026-08-09T09:22:24Z`.

This matters more than a cosmetic slip, which is why it is corrected rather than left.
The whole purpose of recording a tip and a timestamp is to let a later reader compute the
staleness window. With the wrong hour, a reader comparing the checkpoint against
`47bdd073` (merged 09:06 UTC) would conclude that commit landed four minutes BEFORE the
checkpoint and was therefore missed. The opposite is true: the checkpoints ran at 09:02
and 09:02:55 UTC, and `47bdd073` landed four minutes AFTER both. The corrected timeline:

| Event | Real UTC |
|---|---|
| Scan window closes at `942b7e28` | 08:49:42 |
| Checkpoint 1 (pre-commit) — nothing new | 09:02:22 |
| Checkpoint 2 (pre-auto-merge) — nothing new | 09:02:55 |
| `47bdd073` (#1649) merges | 09:06:35 |
| `e64b3e64` (#1652) merges | 09:13:31 |
| PR #1653 merges, report published | 09:22:24 |

**Standing note for future runs of this task:** use `date -u` via the Bash tool, or
`(Get-Date).ToUniversalTime()`, for any timestamp written into a report. `Get-Date -Format
"u"` is a trap — it looks UTC and is not. Every prior report's re-check timestamp taken
that way is suspect by the same offset.
