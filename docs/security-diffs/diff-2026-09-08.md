`src/rasp/nativeProbe.js:168` adds

#### Correction (2026-09-08, post-merge) — O-1 is WITHDRAWN: the exports do not ship

**The load-bearing claim above — "nothing stripping these at build time" — is
false, and it was never checked before publication.** It was an assumption, stated
in the flat voice of a verified fact. With it gone there is no attacker-reachable
function and no observation: Rollup tree-shakes all three exports out of the
production bundle, because nothing outside `src/**/__tests__/**` imports them and
test files are not in the production entry graph.

Verified two ways rather than argued:

- The pre-existing local `dist/` (built 2026-09-03) contains **neither**
  `_resetAttestationLatchForTests` nor `__resetRelockGraceForTests`, while both
  modules are demonstrably bundled — `__veyrnoxRaspLatchHook` is present in
  `dist/assets/getFreshRaspArtifact-*.js` and `veyrnox-relock-grace-ms` in
  `dist/assets/WalletProvider-*.js`. The latch code ships; its reset does not.
- That build predates `nativeProbe.js`'s export (2026-09-03 vs 2026-09-07), so it
  evidences the two siblings and not the symbol #2426 actually added. A **fresh
  `npm ci && npm run build` from `origin/main`** in a throwaway worktree closes
  that gap directly: `_resetNativeHardSignalLatchForTests` appears in **no** file
  under `dist/`, while `__veyrnoxNativeLatchHook` — the latch's own guard variable,
  twelve lines above it in the same module — is present in
  `dist/assets/getFreshRaspArtifact-DsfhvS-b.js`. Same module, one symbol kept and
  the other dropped, which is tree-shaking doing exactly its job.

**Why the wrong conclusion was reached, because the mechanism matters more than
the retraction.** The observation leaned on CLAUDE.md's S-3, where
`ADDITIONAL_TRUSTED_ROOTS_FOR_TESTING` was a mutable trust anchor left in the
release binary. That precedent is **Kotlin**, where an unused `internal` member
genuinely does ship in the APK — R8 shrinking is not tree-shaking and does not
remove a reachable-by-reflection public member the same way. The JS/Rollup build
model is different. The precedent was carried across a language boundary without
checking whether the *mechanism* carried with it, and the analogy did the work the
evidence should have.

That is this runbook's own Step 3 rule failing in a new direction: not "grepped
instead of reading the file", but **reasoned from a sibling case instead of
testing the claim**. A build is as cheap as reading a 900-line file, and the check
is one `grep` over `dist/`. Any future observation of the form "X ships in the
production bundle" must carry a bundle grep, not an inference.

**Residual, stated so the withdrawal is not overclaimed in the other direction.**
The exports *are* reachable in a `vite dev` server, which serves modules unbundled
with no tree-shaking. That is not a shipped artifact and an attacker on a dev
build already has the source, so it is not a finding — but "absent from the
production bundle" is the precise claim, not "absent everywhere".

No action is required, no issue is filed, and #2426 has nothing outstanding
against it. The two sibling exports are likewise clear.
