## Flagged changes

### src/wallet-core/evm/customTokens.js (new, 197 lines) — SAFE
**Commit:** b7dce1b0 feat(wallet): add custom ERC-20 tokens by contract address (#2930)
**Change summary:** Read-only discovery and balance reads for a user-supplied ERC-20 contract. No signing, no send.
**Assessment:** Read in full. `assertPrimarySession()` fails closed (an unreadable session state counts as deniable) and runs before any provider is built, again after `getCode()`, again after `symbol()/decimals()`, again before `balanceOf(owner)` is sent, and once more before a real-session balance is returned. The re-check after `getCode` sits outside the RPC `try/catch`, so the denial cannot be swallowed as an RPC error. Address input is length- and checksum-validated before any provider exists. Contract-returned symbol is treated as hostile (length cap, markup and bidi/control characters rejected). Decimals are bounded 0–36 and re-verified against the chain before every balance read, so a contract that changes `decimals()` cannot silently mis-scale a balance (I4: the read fails with `CUSTOM_TOKEN_DECIMALS_MISMATCH` rather than showing a wrong number). **I2 observation, not a defect:** this feature necessarily sends the user's EVM address (`balanceOf(owner)`) plus the set of contracts they chose to the configured chain RPC, on a 60 s poll while the panel is visible. That links an address to the user's chosen tokens at the RPC operator. It is disclosed in the panel ("Adding reads bytecode… Balances are read from the same RPC"), primary-session only, and the same exposure class as the existing native and registry-token balance reads. It does not touch the wallet backend.

### src/lib/customTokenStore.js (new) — SAFE
**Commit:** b7dce1b0 (#2930)
**Change summary:** Persists up to 50 `{networkKey, address, symbol, decimals}` entries under `veyrnox-custom-tokens`.
**Assessment:** `listCustomTokens()` checks deniability *before* `localStorage.getItem`, so a decoy session does not even inspect whether the key exists. Writes and removes refuse in a private session. Every stored entry is re-validated on read, and corrupt entries are dropped before they reach display or RPC. The key is in `METADATA_RESIDUE_KEYS` in `panic.js`, and `panic.test.js` pins it, so panic wipe clears it. The list is plaintext public data (no keys). Its presence is a tell in the same class as `veyrnox-spam-overrides`, which is already in the same list.

### src/components/CustomTokensPanel.jsx (new) — SAFE
**Commit:** b7dce1b0 (#2930)
**Change summary:** UI for adding and listing custom tokens, mounted on the portfolio page when `canManage`.
**Assessment:** Read in full. The outer component returns `null` when not `visible` or when the session is private, and the stateful inner component (storage read, react-query balance polls) is never mounted in that case. `visible` is `canManage = isUnlocked && !isDecoy && !isHidden`, a second independent gate. The import path captures a pending-work generation before the RPC await and discards the result if a wipe or lock moved it, so a slow import cannot recreate storage after the lock. **Observation, pre-existing and not changed here:** I found no `queryClient.clear()` or `removeQueries` outside tests, so the balance query cache (keyed by token address and owner address) lives in memory until `gcTime` after a lock. Nothing renders it in a decoy session because the panel returns `null` there, so I rate it SAFE. It is memory-only and gone on reload.

### src/lib/locale.js (`resolveFiatCurrency`) — NEEDS-REVIEW (low)
**Commit:** 64738e3b feat(portfolio): fiat-first rows and local currency picker (#2932)
**Change summary:** With no stored preference, the default fiat currency is now inferred from the device locale's region (about 70 regions mapped) instead of always `USD`. The old comment forbade this inference.
**Assessment:** The inference itself is local, deterministic, falls back to USD, and ignores the stored UI-language preference. The disclosure is right: non-USD values are labelled approximate because the FX rates are fixed references, and `FiatApproximationNote` is added to the portfolio and net-worth pages. **Concern, in a file this PR did not touch:** `src/pages/Dashboard.jsx:242` publishes `fiat_currency: fiatCurrency` in its `useAdvisorSnapshot` payload. That payload is merged into `effectivePageSnapshot` and POSTed to `tip-chat` next to the persistent `device_id` when the user has consented. Until now that field was `USD` for everyone who had not picked a currency. It is now a device-region signal (`NGN`, `KES`, `TRY`, …) chosen by no one, sent to a backend that I5 declares untrusted. It is not a deniability fact and not an on-chain identifier, so it does not trip `advisorContext.noCoercionOracles`, and consent gates the transmission. But the behavioural question ("does this send data off-device?") answers yes for a value that did not exist before. I did not verify whether the advisor payload is suppressed in decoy sessions. Suggested: either drop `fiat_currency` from the Dashboard snapshot, or send it only when the user stored an explicit choice. Separately, `Dashboard.jsx` shows the converted total with `ReferenceRateNote` but not `FiatApproximationNote`; I did not read `ReferenceRateNote`'s copy, so whether it covers the fixed-rate caveat is unchecked.
