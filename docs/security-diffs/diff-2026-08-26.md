## ⚠️ REGRESSION DETECTED

### `src/wallet-core/stealth.js:626` — the reveal-time KDF rekey makes the REAL hidden slot the unique blob in a v1-era pool

**Commit:** `7aaffbe1` feat(deniability): reveal-time opportunistic KDF rekey (Gate 2 of #2101) (#2103)

**What changed.** Before #2103, every deniability writer stamped the *device's
recorded* KDF era via `encryptDeniabilityVault()`, so a v1-era device wrote v1
everywhere and its 256-slot stealth pool stayed uniform. After #2103, writers
stamp the current `KDF_PARAMS` (v2: t=6 / 96 MiB, `vault.js:70`) and
`tryRevealHidden()` opportunistically re-encrypts a v1 slot to v2 after a
successful decrypt.

**Why this is a regression.** Chaff has no secret and can never be decrypted, so
`tryRevealHidden()` never rekeys it, and `ensureStealthPool()` only fills slots
where `existing == null` — it never rewrites an existing slot. On a device whose
pool was created before 2026-08-25, the 255 chaff slots therefore stay v1
**permanently**, and the one slot the user actually owns and opens becomes the
only v2 blob in the store. An adversary dumping IndexedDB reads each blob's own
recorded `kdf` and sees 255 × `{iterations:3, memorySize:196608}` against 1 ×
`{iterations:6, memorySize:98304}`. The minority fingerprint *is* the real
hidden wallet. Indistinguishability across the pool is the entire point of the
chaff, and this defeats it with a single field.

The same mechanism applies to `createHiddenWallet()` / `moveWalletToHidden()` on
a v1-era device — no reveal is needed; the first write is already v2 among v1
chaff. That is what the existing test at
`src/wallet-core/__tests__/deniability-kdf-parity.test.js:347` exercises, and it
asserts `uniq.size === 2`.

**On the disclosure, which is the part that needs correcting most.** This was
owner-ruled and is pinned by a regression test, so it was not slipped in — but
the prose recording it describes a different and much smaller thing than the
code does, in two ways:

- `docs/Feature-Status.md:2617` — "A **transient** tell during the rekey window
  is disclosed". It is not transient. There is no window: v1 chaff never
  migrates and the v2 slot never reverts. On a v1-era device the split is
  permanent for the life of the install.
- `deniability-kdf-parity.test.js:22-27` — "on a v1-era device, a hidden wallet
  the user never opens again keeps its v1 slot while everything around it
  migrates. That specific slot becomes a transient tell". This is inverted.
  Nothing around it migrates. The tell attaches to the slot the user **does**
  open, which is the one that must not be identifiable.

The test body at line 353 states the mechanism correctly ("The slot that was
written stamps v2. The other 255 slots STILL stamp v1"), so the artifacts
disagree with each other. A reader who consults the docs or the test header —
which is what a reader consults first — is told the safe version.

**Assessment.** Rated REGRESSION on the code change (it strictly worsens
v1-era-device pool uniformity relative to the immediately preceding H-2
remediation) and on the disclosure independently (I4: a security claim that
understates its own cost). Not asserting the owner ruling was uninformed — only
that what is written down does not describe what ships, and that the residual
identifies the real slot rather than an unopened one. Gate 1 of #2101 (the v2
migration flag) is still OFF, so the primary vault also stays v1 on these
devices, which is what leaves the pool at v1 in the first place.

Devices affected: every install predating 2026-08-25 — which includes the Play
internal-testing track and the TestFlight 1.0.1 builds. Not reproduced on a
device; static reading of `stealth.js`, `vault.js` and the parity test only.

**The REGRESSION and the four remaining NEEDS-REVIEW items still stand**, and one
of them is now understood to be wider than this report described:

- The **stealth-pool KDF distinguisher** is not confined to the stealth reveal
  path. All 258 blobs (256 pool slots + `secondary` + `tertiary`) live in one
  `veyrnox-vault`/`vault` store and are read together in a dump, so `#2103` also
  made `setDuressVault()` and `setPanicVault()` stamp v2 on a v1-era device.
  That reintroduces the original H-2 tell in its sharpest form: `secondary` is
  the duress key by name, so a v2 blob there among 257 v1 ones announces that a
  duress PIN was deliberately configured. The parity tests at lines 202 and 210
  pin that reintroduction as intended behaviour.
- Also confirmed while investigating: the fix cannot be "sweep the chaff forward
  to match". Chaff is indistinguishable from a real slot by construction
  (`makeChaff` is pure `randomBytes`, which is what hides the *count* of hidden
  wallets), so a sweep cannot select its targets and would overwrite other hidden
  wallets whose mnemonics exist nowhere else. Nor can the `kdf` field be edited
  in place — `paramsFromVault` derives the key from it, and `v:2` AAD-binds it
  into the GCM tag (`vault.js:301` says so outright). And an *unrevealed* hidden
  wallet can never be re-encrypted at all, since that needs its secret. A pool
  holding one therefore cannot be made uniform at a new era by any means.

Remediation is in flight under a separate PR (holding the deniability writers at
the pool's era, and retargeting the reveal/duress re-encrypt from a migration
toward `KDF_PARAMS` to a repair toward the footprint's era). It is **not** merged
as of this correction, so the REGRESSION above is open.
