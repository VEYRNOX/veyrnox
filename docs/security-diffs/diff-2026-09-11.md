### R-1 — `src/lib/theftProtection.js:71-78` × `src/components/WalletEntry.jsx:1109-1172` — REGRESSION
**Commit:** `29e6c0a9` `feat(theft-protection): OS biometric step-up on unlock, iOS face-strict (#2498)`

**Change summary:** `WalletProvider.unlock()` now awaits `runTheftProtectionGate({ isPrimary })`
(`WalletProvider.jsx:1930`). The gate runs after the PIN has decrypted the vault. On any failure
it throws `TheftProtectionError`. The failure cases are:
- RASP not ALLOW
- a RASP fetch error
- a biometric decline or error
- iOS biometry other than Face ID
- a biometry probe error

**Assessment — why the throw counts as a wrong PIN.** Read in full, `runPinUnlock`'s catch
(`WalletEntry.jsx:1109-1172`, unchanged in this window) exempts only these cases from the
counter:
- `isPasskeyGateError(e)` or `isBiometricGateError(e)`. Both are duck-typed on their own flags:
  `err.isPasskeyGateError` (`passkey.js:862`) and `err.isBiometricGateError`
  (`biometric.js:194`).
- `e.isPanicWipe`
- `KEK_UI_ERR.KEY_PERMANENTLY_INVALIDATED`, `NO_HARDWARE_FACTOR`, `HARDWARE_FACTOR_DEGENERATE`,
  `USER_CANCELLED`, `MALFORMED_VAULT`
- `UNLOCK_SUPERSEDED`

`TheftProtectionError` sets only `isTheftProtectionError` and has no `code`, so it matches none
of these. It falls through to `registerFailedPinAttempt(...)`, which:
- shows "Incorrect PIN" or the remaining-attempts warning;
- applies the M-7 backoff;
- on the tenth consecutive miss, calls `panicWipe({ confirmed: true })`.

No file in the repo imports `isTheftProtectionError` except its own test.

**What triggers it.** Each case below needs the feature to be on and a correct PIN typed:
- **RASP tier WARN or BLOCK at unlock.**
  - `getFreshRaspArtifact` races the native and attestation probes against a 1500 ms fail-closed
    timeout. `ATTESTATION_ENABLED = true` (`attestation.js:78`). A slow or unavailable probe
    becomes `INTEGRITY_UNAVAILABLE`, which degrades to WARN.
  - CLAUDE.md records "pin/chain miss → INTEGRITY_UNAVAILABLE → WARN" as the accepted posture on
    genuine Android devices (#2276).
  - So this is not limited to rooted devices. On an affected device every unlock fails.
- **Biometric cancel or mismatch** at the extra prompt.
- **An iPhone with Touch ID only.** Every unlock returns `requires-face`.
- **Any web build.** `verifyBiometric2fa` throws `unavailable` when `!Capacitor.isNativePlatform()`
  (`biometric.js`). `TheftProtectionSettings` still renders on web: `Settings.jsx:440` mounts it
  with no `isNative` gate, unlike `FastpathToggle`, which renders nothing off Android. A web user
  who enables the toggle is refused on every correct PIN, and the tenth attempt wipes the device.

**There is no way out once it is enabled.** The only way to turn the setting off is in Settings,
which needs an unlock. Every unlock attempt counts toward the wipe.

**The one-tap biometric path misreports it too.** `unlockWithBiometric` calls
`unlock(password, { skipBiometric: true })`, so the gate runs there as well. If the gate throws,
`handleBiometricUnlock`'s else-branch (`WalletEntry.jsx:876-885`) treats it as a stale cache:
- it calls `clearUnlockSecret()`;
- it tells the user "Face ID was out of date and has been reset".

That deletes the user's biometric-unlock cache and gives a false reason (I4, fail-honest). It
does not cause data loss.

**This is a class the file already knows about.** The same catch block excludes three other
correct-credential failures, and each comment says counting them "destroys funds after 10
retries" or is "the data-loss bug": KEK invalidated, hardware factor unavailable, and user
cancel. #2498 adds a fourth failure class through the same `unlock()` throw without extending
that exclusion list.

**The tests cannot see it.**
- `theftProtection.gate.test.js` (17 `it` blocks) tests the pure gate with injected dependencies.
- `WalletProvider.theftProtection.test.js` pins the source text of the call site. It is a
  regression pin, not a behavioural test.
- Nothing exercises how `WalletEntry` classifies the thrown error. A green suite is therefore not
  evidence here.

**Why this is REGRESSION rather than NEEDS-REVIEW:**
- An existing control, the attempt counter, now counts correct credentials.
- The outcome is irreversible local data loss. I4's fail-honest half is broken on the screen that
  triggers the wipe.
- Blast radius is limited: the feature is opt-in and off by default.
- It merged at 2026-09-10T16:57Z. That is after the build-58 upload recorded in #2500's commit
  message, so it is probably not in a submitted store binary. **This was not checked against
  App Store Connect.**
- Whether it has already reached the web deploy was **not verified**.

**What a fix probably looks like** (report only, not implemented):
- Classify `isTheftProtectionError(e)` as a non-wrong-PIN failure in `runPinUnlock`, `runUnlock`
  and `handleBiometricUnlock`, with honest copy for each `reason`.
- Add a `WalletEntry`-level test that a `TheftProtectionError` after a correct PIN never calls
  `registerFailedPinAttempt`. Mutation-check it.
- Gate the toggle by capability: native only, and on iOS require Face ID to be available when it
  is switched on.

### N-1 — Theft Protection: several claims do not match the code — NEEDS-REVIEW
**Commit:** `29e6c0a9` (#2498). Files: `src/lib/featureCatalogue.js` (new entry),
`src/lib/theftProtection.js` header, `src/components/security/TheftProtectionSettings.jsx`.

**a. "iOS is face-STRICT" and "lockout … is treated as declined and fails closed" are not what
the reused helper does.**
- `verifyBiometric2fa` (`biometric.js`) catches `biometryLockout`, retries with
  `allowDeviceCredential: true`, and returns `true`.
  - On iOS that is `LAPolicy.deviceOwnerAuthentication`, which accepts the device passcode.
  - It is `BiometricAuthNative.swift` in `@aparajita/capacitor-biometric-auth` 10.0.0, the
    version in the lockfile.
- When biometrics are not enrolled but the device is secure, the helper goes straight to the
  passcode.
- The iOS post-check does not catch either case. The plugin's `checkBiometry` returns
  `biometryType: context.biometryType.rawValue` whether or not biometrics are available, so a
  Face ID iPhone still reports `2` and passes.
- **Attack sketch** (from reading the code, not tested on a device): a thief who has shoulder-surfed
  both the Veyrnox PIN and the device passcode fails Face ID until it locks out, then passes the
  gate with the passcode. That is the main case a theft factor exists for.
- Android has the same lockout-to-device-credential fallback.

**b. "Touch-ID-only iPhones cannot enrol"** (component header, catalogue). The toggle writes the
preference with no capability check. Those devices can switch it on, and are then refused at every
unlock (see R-1).

**c. "at every unlock"** (catalogue summary). Two things undercut this:
- `unlockBiometricOnly` (`WalletProvider.jsx:2277`) never calls the gate.
- `handleBiometricUnlock` tries that path first (`WalletEntry.jsx:864`), and it auto-fires when
  the unlock view opens (`:898-905`). The fast-path button is hidden (`fastpathButtonVisible =
  false`), but the path is live.

Impact is low: the keystore fast path itself requires a biometric, enforces RASP ALLOW
(`native.js` `unlockBiometricOnly`), is Android-only, and never takes a PIN. The claim is still
wrong.

**d. Decrypted container kept after a failed gate.**
- `containerRef.current = container` (`WalletProvider.jsx:1901`), plus
  `setActionPasswordConfigured` and `setHiddenWallet2faModeState`, run **before** the gate at
  `:1930`.
- On a throw, nothing clears them. Only `lock()` does (`:595`).
- So a Theft-Protection-refused session leaves the decrypted multi-seed container in provider
  memory while `isUnlocked` is false.
- I1 is not violated, since nothing leaves the device. Moving the gate above `:1901`, or clearing
  the ref on throw, would close it.

**e. Observation, not a finding.** The gate does nothing on decoy and hidden sessions, as a
deliberate K-2 choice. The flip side: a coercer who has watched the owner get a Face ID prompt
after the PIN would notice that a decoy PIN unlock shows none. Worth one line from the honest
reviewer; no change proposed.

### N-3 — `index.html` boot watchdog is blocked by the app's own CSP — NEEDS-REVIEW
**Commit:** `bf68a1be` `fix(1.0.1): guard against blank-page on launch + XCUITest regression (#2500)`

**Change summary:** #2500 adds an inline `<script>` at the end of `<body>`. If `#root` is still
empty after 5 s, it swaps in fallback HTML with an inline `onclick="location.reload()"` button.

**Assessment:** The script cannot run anywhere the app's CSP is enforced.
- Both CSP copies set `script-src 'self' 'wasm-unsafe-eval'`, with no hash, nonce or
  `'unsafe-inline'`: the meta tag at `index.html:32` and `public/_headers:7`.
- `csp-policy.test.js:91` asserts `'unsafe-inline'` stays absent.
- `index.html`'s own comment records inline-script blocking as verified on the iOS Simulator.
- The inline `onclick` is blocked for the same reason.

The CSP winning is the correct security result, and nothing was weakened. What is wrong is the
claim built on it:
- The commit message says "The user never sees a blank screen".
- `docs/Feature-Status.md`'s 2026-09-10 entry and CLAUDE.md's gate-3 waiver (`67aea07f`) both list
  the watchdog as one of the four fix attempts.
- `FirstPaintNotBlankTests.swift` step 3 asserts the watchdog's "Reload Veyrnox" fallback is
  absent. That can never fail, so the assertion is vacuous.

`RootErrorBoundary.jsx`, the other half of #2500, is SAFE. It does real work for errors thrown
after mount.

If the watchdog is wanted:
- Move it into a same-origin file (for example `/boot-watchdog.js`, allowed by `'self'`) and wire
  the button with `addEventListener`.
- **Do not add `'unsafe-inline'`.**
- Before enabling it, check that no legitimate state leaves `#root` childless for 5 s. The script
  overwrites React's container with `innerHTML`.
