### `functions/api/buy/webhook.js` — NEEDS-REVIEW
**Commits:** `407e91e7` (#2278), `d8134071` (#2279), `8689f618` (#2281)
**Change summary:** Adds HMAC-SHA256 verification of the `X-Transak-Signature`
header behind a three-state `TRANSAK_WEBHOOK_VERIFY_MODE` (`off` default /
`warn` / `strict`), with constant-time hex comparison and a raw-body read shared
between verification and JSON parse.

**Assessment of the design — SAFE.** Defaulting to `off` is not a regression:
it is the pre-existing behaviour, the endpoint's only side effect is console
logging, and the staged rollout exists precisely because Transak's signing
scheme is unconfirmed — shipping a guessed verifier in `strict` would 401 every
legitimate webhook. The missing-secret path degrades to log-only rather than
500, and the mode is deliberately not echoed in the response so an
unauthenticated caller cannot learn whether verification is on. All three
choices are the right way round.

**The finding is in `warn` mode's log line:**

```js
console.warn(
  `[buy/webhook] ref=${ref} verify_warn reason=${verify.reason} ` +
    `header=${logSafe(verify.header)} computed=${logSafe(verify.expected)} ` +
```

`verify.expected` is `HMAC-SHA256(rawBody, TRANSAK_WEBHOOK_SECRET)` over a body
the caller fully controls, and the endpoint is unauthenticated. In `warn` mode
anyone can POST a chosen body and cause a valid HMAC for that exact body to be
written to the logs. `logSafe` does not blunt this — its cap is 64 characters
and a SHA-256 hex digest is exactly 64, so the digest is logged in full.

That is a signing oracle with a log-read precondition. It does not matter while
`mode=warn` (nothing is enforced), but the stated plan is to flip to `strict`
once warn telemetry confirms the scheme — at which point any signature harvested
during the warn window is a forged webhook that verifies. An attacker able to
read Cloudflare Pages logs can pre-compute forgeries for the exact payloads they
intend to send later.

**Recommended fix (cheap, preserves the purpose):** log a short prefix of both
values rather than the whole digest — e.g. `header.slice(0,8)` and
`expected.slice(0,8)`. Eight hex characters is ample to confirm whether the two
agree and therefore whether the scheme is right, which is all `warn` mode exists
to establish, while being useless for forgery. Alternatively log only
`match=true|false` plus the header's length and prefix.

Not rated REGRESSION because the exposure requires privileged log access and the
enforcement it would defeat is not yet enabled. It should be fixed *before*
`strict` is turned on, not after.
