### N-1 — `sql/partner-referral-codes.sql:94-169` — NEEDS-REVIEW
**Commit:** `230637fd` `feat(referrals): get_referral_tier RPC + partner tier lock (platinum default) (#2528)`

**Change summary:** The migration adds `tier_override` and a three-argument,
service-role-only `mint_partner_referral_code(..., p_tier_override default
'platinum')`. `get_referral_tier` then exposes only the resulting tier key through
the allowlisted RPC; `referralApi.fetchReferralTier` allowlists that key before it
can select a RevenueCat offering.

**Assessment:** The comment says the old two-argument signature is dropped, but
line 98 drops `(text, text, text)`, not the pre-existing `(text, text)` function
introduced by `803bfb07`. On a database where #2526 was already applied, the old
service-role-only overload survives. A two-argument call resolves to that exact old
signature and inserts a NULL `tier_override`; a one-argument call can be ambiguous
because both overloads have defaults. This defeats the documented default-platinum
partner lock and can leave a partner referral offer fail-closed as `none`.

This is a migration/commerce-integrity defect, not an authorization widening: the
surviving old function remains service-role-only and is still absent from the Pages
RPC allowlist. Before production apply, replace the mistaken drop with an explicit
`DROP FUNCTION ... (text, text)`, re-issue its ACL only for the intended
three-argument signature, and verify `pg_proc` contains exactly that signature.
The scan did not query staging or production.

### N-2 — `src/pages/SendCrypto.jsx:994-1000, 1375-1528, 1745-1778` and `src/lib/WalletConnectProvider.jsx:672-702` — NEEDS-REVIEW
**Commit:** `4ba80bbf` `feat(theft-protection): enforce spend limits with a fresh biometric gate`

**Change summary:** An over-limit primary-session send now obtains a one-shot
Theft Protection token before the shared signing chokepoint; WalletConnect receives
the same in-band path. Failed or unavailable valuation/cap reads still reject.
Tests pin the one-shot token, stale-checkbox rejection, primary-session condition,
and WalletConnect rejection paths.

**Assessment:** The new flow is fail-closed in the JavaScript gate and is an
improvement over the previous silent checkbox. However, its claimed fresh
Face-ID/biometric acknowledgement inherits the open `verifyBiometric2fa()` behavior:
after `biometryLockout`, or when no biometric is enrolled on a secured device, it
retries with `allowDeviceCredential: true` (`src/lib/biometric.js:163-177`). The
post-check only identifies the device's configured iOS hardware, not the factor used
in that prompt. Thus an OS device credential can authorize an over-limit send,
including a WalletConnect request, despite the UI and commit describing a biometric
gate. The native prompt's reason is generic and does not bind the dapp or amount.

This does not remove the old limit control—without a successful OS prompt the send
still rejects—but it materially broadens the previously recorded N-1 residual from
unlock to money movement. Decide whether device credential is an accepted step-up
factor. If not, remove the fallback for Theft Protection specifically and add a
real-device negative test for biometric lockout/no-enrolment before describing this
path as biometric-gated. INTERNAL static analysis only; no device test was run.
