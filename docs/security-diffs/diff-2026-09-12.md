### N-1 — `sql/partner-referral-codes.sql:94-169` — NEEDS-REVIEW
**Commit:** `230637fd` `feat(referrals): get_referral_tier RPC + partner tier lock (platinum default) (#2528)`

**Change summary:** The migration adds `tier_override` and a three-argument,
service-role-only `mint_partner_referral_code(..., p_tier_override default
'platinum')`. `get_referral_tier` then exposes only the resulting tier key through
the allowlisted RPC; `referralApi.fetchReferralTier` allowlists that key before it
can select a RevenueCat offering.

**Assessment:** The comment says the old two-argument signature is dropped, but
line 98 drops `(text, text, text)`, not the pre-existing `(text, text)` function
introduced by `803bfb07`. On a database where #2526 was already applied, the old
service-role-only overload survives. A two-argument call resolves to that exact old
signature and inserts a NULL `tier_override`; a one-argument call can be ambiguous
because both overloads have defaults. This defeats the documented default-platinum
partner lock and can leave a partner referral offer fail-closed as `none`.

This is a migration/commerce-integrity defect, not an authorization widening: the
surviving old function remains service-role-only and is still absent from the Pages
RPC allowlist. Before production apply, replace the mistaken drop with an explicit
`DROP FUNCTION ... (text, text)`, re-issue its ACL only for the intended
three-argument signature, and verify `pg_proc` contains exactly that signature.
The scan did not query staging or production.

### `workers/referral-redirect/src/index.js` — SAFE
**Commit:** `69fbd29c` (#2531)

**Change summary:** A new Cloudflare Worker bound to `veyrnox.com/r/*` and
`www.veyrnox.com/r/*` imports the existing Pages function
`functions/r/[code].js` rather than copying it, and rewrites that function's
relative `Location` to an absolute one on `https://veyrnox-prod.pages.dev`. It
exists because the app hands out `veyrnox.com/r/CODE` share links while the
redirect only ever lived on the Pages host, so every share link 404'd on the
marketing site.

**Assessment:** No open redirect and no header injection. The wrapper's only
mutation is `new URL(res.headers.get('Location') || '/', APP_ORIGIN)`, and the
inner `Location` is never attacker-derived: `functions/r/[code].js` emits either
the literal `/` or `` `/?ref=${encodeURIComponent(code)}` `` with `code` having
passed `CODE_RE` (`/^VYX-[ABCDEFGHJKLMNPQRSTUVWXYZ23456789]{6}$/`). The
destination origin is a module constant, not request-derived, so a hostile path
cannot steer it.

Verified behaviourally rather than by reading — the handler was run directly
over the edge cases:

| path | result |
|---|---|
| `/r/VYX-STRKLB` | `302 https://veyrnox-prod.pages.dev/?ref=VYX-STRKLB` |
| `/r/VYX-STRKLB/extra` | `302 https://veyrnox-prod.pages.dev/` |
| `/r/` | `302 https://veyrnox-prod.pages.dev/` |
| `/r/VYX-STRIKE` (I not in alphabet) | `302 https://veyrnox-prod.pages.dev/` |
| `/r/%2F%2Fevil.com` | `302 https://veyrnox-prod.pages.dev/` |
| `/r/VYX-STRKLB%26x` | `302 https://veyrnox-prod.pages.dev/` |

The protocol-relative probe is the one that matters, and it fails closed to the
app root. The function's `Cache-Control: no-store` and `Referrer-Policy:
no-referrer` survive the header copy — both are load-bearing here rather than
mere hygiene: `no-store` stops a shared cache serving one visitor's referral
code to another, and `no-referrer` stops the code leaking to the marketing
origin. The new test pins both.

No secrets, no bindings, no vars; `workers_dev = false`, so there is no public
`*.workers.dev` hostname alongside the zone route. Routes are scoped to `/r/*`
only and do not overlap the root `wrangler.toml` (`veyrnox-prod`, which declares
no routes). Not part of the locked TIP chain. No CI workflow deploys it —
`git grep` over `.github/`, `scripts/` and `package.json` finds no reference, so
deployment is the manual `npx wrangler deploy` the file documents. Nothing here
touches key material, signing, RASP, or the client.

### `workers/referral-redirect/src/index.js:24-27` — NEEDS-REVIEW (low)
**Commit:** `69fbd29c` (#2531)

**Change summary:** The Worker reconstructs the Pages runtime's `params.code`
shape from the path — a string for one segment, an array for anything deeper —
so the imported function's nested-path branch behaves identically on both hosts.
The file states this as a requirement: *"Reproduce exactly that shape from the
path so its nested-path branch keeps behaving the same on both hosts."*

**Assessment:** The reconstruction is `pathname.split('/').filter(Boolean)`, and
`filter(Boolean)` collapses empty segments, so the shapes are **not** identical:

| path | Worker | Pages `params.code` shape |
|---|---|---|
| `/r//VYX-STRKLB` | `302 …/?ref=VYX-STRKLB` | array → fails closed to `/` |
| `/r/VYX-STRKLB/` | `302 …/?ref=VYX-STRKLB` | array → fails closed to `/` |

Both confirmed by running the Worker, not by reading it.

This is **not a security defect.** The divergence is permissive rather than
restrictive, the code still has to clear `CODE_RE`, and the destination is still
the fixed app origin — so the worst case is that a doubled or trailing slash
credits a valid referrer where the Pages host would have dropped the ref. What
it is, is a **claim in code that is not true**, in the one file whose entire
design rationale is "one source of truth, identical behaviour on both hosts".
Either drop the `filter(Boolean)` (splitting on `/` and slicing yields the real
segment list, empties included) or amend the comment to say the shapes match for
the cases that matter and diverge on empty segments. The Worker's test file pins
`/r/` and `/r/<code>/extra` but neither divergent case, so nothing currently
holds this claim honest.
