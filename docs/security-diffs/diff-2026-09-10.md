### `.github/workflows/firebase-test-lab.yml:143` — NEEDS-REVIEW
**Commit:** `622da941` `fix(ci): pin dispatched CI runs to an exact SHA via target_sha`
**Change summary:** run identification moved from a server-side
`gh run list --commit "$SHA" --limit 20` filter to a client-side
`--limit 40 … .displayTitle | contains("$SHA")` match over `ci.yml`'s new
`run-name: ci · ${{ inputs.target_sha || github.sha }}`.

**Assessment:** the underlying problem is real and correctly diagnosed —
`gh workflow run --ref` cannot take a SHA, so a dispatched run's `head_sha` is
main's tip at creation, which on this branch is routinely a different commit
(runs `34197672875`, `34328144917`). The fix is directionally right and the
accompanying `target-sha-guard` is a genuine supply-chain control (see below).
Two properties of the *identification* half are worth a second look:

1. **`run-name` renders the RAW, unvalidated `inputs.target_sha`.** `run-name` is
   evaluated when GitHub creates the run, i.e. before `target-sha-guard` executes,
   so the 40-hex validation cannot constrain what lands in the title the FTL gate
   matches on. **Bounded, and I want to state the bound rather than the alarm:** a
   run whose `target_sha` is malformed fails the guard, so its conclusion is
   `failure`, and the wait loop only accepts `conclusion == success` — it errors
   out with `refusing to test another commit's APK`. So the reachable outcome is
   denial of the gate, not APK substitution. Substitution would need a *successful*
   run whose title contains a SHA it did not build, and the guard's 40-hex +
   `merge-base --is-ancestor` check prevents exactly that. Recording it because
   "the validated value" and "the value in the run name" are two different values,
   and only one of them is what the gate reads.
2. **A fixed 40-run listing window replaces an unbounded server-side filter.**
   `--commit` was matched by the API across all runs; `contains()` is applied to
   whatever the most recent 40 `ci.yml` runs happen to be. On a branch merging
   10+/day plus PR runs, during a ~15 min build, the target run can fall out of
   that window — and the failure mode is silent (no match, loop keeps polling,
   budget expires) and looks identical to "CI hasn't finished". Suggest
   `--limit` sized from the retry budget, or keeping a server-side narrowing
   filter alongside the title match.

The pin `src/__tests__/ci-target-sha-pinning.test.js` is well built — it strips
comments before asserting, explicitly citing the 2026-09-03 absence-check
failure, and counts checkouts against pins rather than matching a string.

### `.github/workflows/ci.yml` (+227) — SAFE (control ADDED), one mixed-identity gap
**Commits:** `622da941`, `aabc8a02` `fix(ci): guard target SHA checkout refs`, `1a66aa56` `fix(ci): isolate dispatch SHA from checkout action`
**Change summary:** new `target-sha-guard` job; every consumer job now checks out
`ref: ${{ github.sha }}` and then `git checkout --detach "$VALIDATED_SHA"`.

**Assessment — this is a real supply-chain control and the right construction.**
The untrusted `inputs.target_sha` never reaches `actions/checkout`'s `ref:`
input (the pin asserts `not.toContain('ref: ${{ inputs.target_sha }}')`). The
guard enforces both `^[0-9a-f]{40}$` **and**
`git merge-base --is-ancestor "$TARGET_SHA" origin/main`, so a dispatch cannot
execute an arbitrary ref inside a workflow that restores shared caches and holds
signing secrets. On `pull_request` the input is empty, `effective_sha` falls back
to `github.sha`, and behaviour is unchanged.

**Finding — `publish-to-play-closed` decides on one commit and uploads another.**
That job did not join `needs: target-sha-guard`, and its new versionCode gate
reads `build.gradle` at `SHA: ${{ github.sha }}`. On a `workflow_dispatch`
carrying `target_sha`, the AAB it downloads was built by `android-release` from
the **validated** SHA, while the skip/upload decision is made against the
**branch tip**. That is the same "build one tree, decide on another" class
`target_sha` was created to remove. Consequence is bounded by the gate's
deliberate fail-open (worst case a spurious upload attempt that says exactly
why), so this is low severity — but the fix is one line: read the gate's
`SHA` from `needs.target-sha-guard.outputs.effective_sha`.

**Observation O-2 — `target-sha-guard` is now a single point of failure in front
of three required checks.** `verify`, `unit-tests` and
`Release-cert guard rejects wrong fingerprints` all gained `needs:` on it. If it
ever fails or is skipped, those three never report, and per `CLAUDE.md` a
required context that does not report leaves every PR at `BLOCKED` with no red
anywhere to explain it. Low likelihood (on PRs the job exits 0 immediately), but
it is exactly the failure shape that repo has been bitten by before.
