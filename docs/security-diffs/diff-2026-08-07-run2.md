## Flagged changes

### `functions/api/_middleware.js:30` — NEEDS-REVIEW (highest item in this report)
**Commit:** `e99dd422` feat(edge): Cloudflare Pages Functions API layer for all external calls (#1566)

**Change summary:** Introduces shared CORS middleware for every `/api/*` edge
route, with an origin allowlist.

**Assessment:** The allowlist match is a no-op for one whole clause:

```js
const match = allowed.find(o => origin === o || origin.endsWith('.pages.dev'));
```

The second clause never references `o`. Once the iteration reaches the first
element, `origin.endsWith('.pages.dev')` decides the whole predicate — so **any**
origin ending in `.pages.dev` is reflected back in
`Access-Control-Allow-Origin`. Cloudflare Pages hands `<project>.pages.dev` to
anyone who creates a project, so this is an attacker-registrable namespace, not
an internal one.

Scoping the impact honestly, because it is narrower than it first looks:

- **No credential is exposed.** The middleware sets no
  `Access-Control-Allow-Credentials`, and this app has no user sessions or
  cookies. Nothing is riding on the victim's identity.
- **CORS is not what keeps these endpoints closed.** Every route under
  `/api/*` is unauthenticated by design; `curl` reaches them regardless of
  origin. So this does not "open" anything that was closed to a determined
  attacker.

What it does cost is real but bounded:

- **It defeats the per-IP rate limits added on purpose.** M-6, M-7 and L-10
  (2026-07-28 wave) added per-IP dimensions to `generate_referral_code`,
  `track_event` and the bonus-claim limiter. A page on `evil.pages.dev` can
  drive those requests from arbitrary *visitors'* browsers and IPs, which is
  exactly the dimension those limits were added to constrain.
- **`/api/buy/session` has no rate limit at all** (see the next finding), and
  each call mints a real Transak partner session against the production
  partner account.

**The bug is currently load-bearing — this is the part that matters for whoever
fixes it.** `DEFAULT_ALLOWED_ORIGINS` contains `https://veyrnox-staging.pages.dev`
and no `veyrnox-prod` entry. The Pages project was renamed to **`veyrnox-prod`**
in this same window (`wrangler.toml:2`, `deploy-preview.yml:193
--project-name=veyrnox-prod`, and `rollback.yml`'s staging→prod retarget). So
`https://veyrnox-prod.pages.dev` — the live deployment — is admitted **only** by
the buggy wildcard clause. Correcting the predicate to `origin === o` in
isolation would start returning `Access-Control-Allow-Origin: https://veyrnox.com`
to the production Pages origin and break `/api/*` from it. The stale allowlist
entry and the wildcard have to be fixed in one change.

**No test covers this file.** `functions/` contains exactly one test —
`functions/api/data/__tests__/klines-okx-fallback.test.js`. The `vitest.config.js`
glob that lets `functions/**` run at all was only added on 2026-08-06
(`65e1cb45`), after this middleware shipped, so there was never a point at which a
test could have caught it.

### `functions/api/buy/session.js` — NEEDS-REVIEW
**Commit:** `cb167ce0` feat(buy): Transak on-ramp — staging-only, ship-gated (#1509), and follow-ups

**Change summary:** New edge endpoint holding `TRANSAK_API_SECRET` /
`TRANSAK_API_KEY`, refreshing a partner access token (cached 6 days via the Cache
API) and minting a one-time widget URL.

**Assessment:** The core secret-handling design is sound and worth saying so: the
secret never leaves the edge, `SUPPORTED_ASSETS` is a fixed 11-row map, endpoint
hosts come from a fixed `ENDPOINTS` table, and `TRANSAK_ENVIRONMENT` defaults to
`'STAGING'` — failing to staging rather than production. Two things are not.

**(a) No rate limit on a credentialed, unauthenticated, side-effectful endpoint.**
`CLAUDE.md`'s API rules are explicit: *"Rate limiting on every RPC… New RPCs must
define and enforce a rate limit before merge — no unthrottled write endpoints."*
Every POST here spends a real upstream `POST /api/v2/auth/session` against the
Veyrnox partner account. There is no per-device, per-IP or global cap, and no
dedup key. Combined with the CORS defect above, request volume can be sourced
from arbitrary visitors' IPs. This is partner-quota abuse rather than a key or
signing risk, but it is the one endpoint in the new layer that costs something
real per call.

**(b) Upstream error bodies are echoed to the client.** Both failure paths do:

```js
err(502, `Transak refresh-token ${res.status}: ${text.slice(0, 300)}`);
err(502, `Transak session ${sessionRes.status}: ${text.slice(0, 300)}`);
```

`err()` sets `e.expose = true`, and `_middleware.js` returns `err.message`
verbatim when `expose` is set. So up to 300 characters of a third-party API's
error body reach the client. That contradicts the response-hygiene rule
(*"API responses must not leak internal IDs… Wrap errors in a generic envelope
with a client-safe message"*). The partner secret itself is not echoed — it is
sent in a request header, not returned — so this is diagnostic-detail leakage,
not credential leakage. The `expose` flag is the right mechanism; these two call
sites are just using it on data they do not control. Log the upstream text, return
a generic 502.

### `src/wallet-core/shamir.js:~370-395` — NEEDS-REVIEW (documentation, no runtime effect)
**Commits:** `0a70fd2d` (module introduced), `9d37f016` (H-6 commitment), `97750cbb` (M-7 constant-time GF)

**Change summary:** New Shamir 2-of-3 GF(2^8) implementation for DEK sharding.
The 2026-08-03 audit then added a SHA-256 commitment (H-6) and replaced the
table-driven, zero-branching GF arithmetic with a branch-free, table-free
implementation (M-7).

**Assessment:** The **code** is in good shape and the audit fixes are genuinely
present — the commitment is recomputed over the reconstructed secret and compared
with `timingSafeEqual` *before* the extra-share cross-check, `gfMul` is a fixed
8-iteration masked loop with no table reads, `gfInv` is a fixed square-and-multiply
chain, buffers are zeroed in `finally`, and shares are defensively copied against
SharedArrayBuffer TOCTOU. The module header documents all of this accurately,
including an honest limit on what "constant-time" can mean in JavaScript.

The problem is that the **public API JSDoc was never updated**, and it now states
the pre-audit position as fact. Every one of these lines sits directly above
`export function combine()`:

- *"integrity rests on CRC32 (corruption detection only — not cryptographic
  authentication)"* — false; H-6's commitment check is 40 lines below it.
- *"The caller MUST authenticate the reconstructed DEK against the vault's
  AES-256-GCM AAD before using it"* — the module header explicitly records that
  this advisory contract was **replaced** by the in-module check, on the reasoning
  that *"an advisory contract no caller is obliged to honour is not a control"*.
- *"a hash commitment would leak information about the secret"* — directly
  contradicted by `computeCommitment`'s own comment, which argues it does not.
- *"NOT constant-time: gfMul branches on zero, table lookups are cache-visible"* —
  both the branch and the tables were removed by M-7.
- `@param`/`@returns` on both `split()` and `combine()` say **"envelope v1"**; the
  format is v2 and the header states v1 is *rejected, not migrated*.

This is doc-only, so no behaviour is wrong today, and **the module has no callers**
— `git grep shamir -- src` outside its own tests and file returns nothing, which
matches the header's *"nothing calls this module yet"*. That bounds it to
NEEDS-REVIEW rather than anything higher.

It is worth flagging anyway because of *who reads it*. This is the docstring an
IDE shows on hover at the moment someone first integrates the module — and it
tells that integrator (a) reconstruction is unauthenticated so they must add their
own AAD check, and (b) that adding a commitment would leak the secret. Reading
(b) as current guidance is an argument for *removing* the H-6 fix. Same class as
L-3 in the 2026-07-28 wave (`PlayIntegrityPlugin` KDoc still describing a
pre-#1097 bypass), which was fixed for exactly this reason.

### `src/wallet-core/vault.js:257-312, 421-445` — SAFE (control ADDED)
**Commit:** `770db268` fix(vault): guard decryptVault against structurally incomplete blobs (#1521)

`requiredB64Field` now decodes and returns bytes with a stable
`VAULT_ERR.MALFORMED`, closing three paths: absent field, corrupt base64, and —
the one that mattered — `atob()`'s silent coercion, where a numeric `salt: 123`
decoded to a 2-byte salt and surfaced much later as a generic "wrong password",
blaming the user for a structurally broken store. The ordering comment is
correct and non-obvious: structural validation must precede `paramsFromVault`
because argon2id allocates `memorySize` KiB before the GCM tag is checked, so a
malformed blob carrying an OOM-sized `memorySize` has to be rejected first.
Distinguishing MALFORMED from the wrong-password sentinel is **not** an oracle —
reaching that branch is knowable without any password. `ct.slice()` at the
`crypto.subtle.decrypt` call adds a copy against buffer mutation mid-decrypt.

- The failing check targets a Cloudflare **Workers** service named `veyrnox` —
  a different name and a different product from the `veyrnox-prod` **Pages**
  project this repo actually deploys to.

That combination is consistent with a stale or misconfigured Workers Builds
integration pointed at a repo with no Worker to build. **It is not confirmed
from here** — the build log sits behind `dash.cloudflare.com` auth and this scan
is static analysis with no Cloudflare access. The alternative reading matters
more if true: that a real Worker (`CLAUDE.md` describes `tip.veyrnox.com` as a

happening. Someone with dashboard access should read the log and settle which.

**Why a documentation scan is flagging a red build at all:** a check's value is
entirely in the signal it carries, and one that is red on every PR carries none.
Worse, it teaches reviewers to read red as normal. This repo already has that
failure mode in its history — the release-cert guard survived ~15 merges in an
inert state precisely because red runs on `main` were common enough that each
fresh one looked like someone else's problem
(#1310 → #1313 → #1325 → #1338 → #1386/#1391). Either fix the integration or
remove it; leaving it permanently red is the option with the ongoing cost.

## Addendum 3 (2026-08-07, pre-merge) — two of this report's findings are already fixed, and it was wrong about one remedy

Three more commits landed while this PR sat in its required checks. Between them
they close the highest-severity item in this report and both of run 1's
remaining open items. All verified by reading the diffs, not the subject lines.

| Item | Fixed by | Status |
|---|---|---|
| `_middleware.js` CORS wildcard (this report) | `d1dc45bf` (#1598) | **RESOLVED** |
| `simulate.js` `willRevert` unreachable (run 1 REGRESSION) | `25fade75` (#1597) | **RESOLVED** |
| `tip-screen` `http://localhost` re-added (run 1) | `0a69a6f9` (#1596) | **RESOLVED** |

**`d1dc45bf`** replaces the wildcard with
`/^https:\/\/(?:[a-z0-9-]+\.)?veyrnox-(?:prod|staging)\.pages\.dev$/` — one
anchored pattern covering both the project alias and preview subdomains, with
the slug charset tied to the `tr -c 'a-zA-Z0-9-'` sanitiser in
`deploy-preview.yml`. It reaches the same conclusion this report did about the
`veyrnox-prod` rename making the bug load-bearing, and adds 16 test cases,
mutation-verified (4 go red with the wildcard restored).

**`25fade75` independently found the trap this report's suggested remedy would
have walked into, and that is worth recording against this report, not just for
it.** Run 1 proposed distinguishing a revert from a transport failure by
`code === 'CALL_EXCEPTION'`. **That discriminator is wrong.** ethers v6 raises
`CALL_EXCEPTION` for an *unreachable* RPC too, with `shortMessage: 'missing
revert data'` and `data: null` — so gating on the code alone reinstates the
original bug, reporting every RPC outage as "Transaction predicted to FAIL".
The merged fix keys on whether the node **answered** (`data != null`, treating a
bare `'0x'` as a genuine revert) and resolves ambiguity toward
`simulationFailed`, on the reasoning that claiming no verdict when we had one is
a smaller harm than inventing one we never got.

It also closes the `noKnownRisks` half by adding a `degraded` flag rather than
gating on `!simulated` — because BTC and SOL return `simulated: false` **by
design** (decode-only, nothing to dry-run), so reading `!simulated` as
"degraded" would suppress the clean-state summary on every BTC and SOL preview.
Run 1's suggested wording, "`noKnownRisks` should additionally require
`result.simulated`", would have caused exactly that regression.

Both corrections stand in the record rather than being quietly dropped. **A
