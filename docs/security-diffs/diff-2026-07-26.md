## Flagged changes

### `sql/growth-backend-changes.sql:52` — NEEDS-REVIEW (high)

**Commit:** `9c524212` feat: growth product changes (#1340)

**Change summary:** Adds `decrement_referral(p_code text)` — a SECURITY DEFINER
RPC that decrements any referral code's count, intended as a refund clawback.

**Assessment:** No rate limit, no device binding, no dedup table, no caller
authentication. There are **no `GRANT`/`REVOKE` statements anywhere** in `sql/`
or `supabase/` (verified by grep), so Postgres' default `EXECUTE TO PUBLIC`
applies and PostgREST exposes it to the `anon` role — the key that ships in the
client bundle by design.

Referral codes are shared publicly by their owners; that is the feature. So an
attacker who sees any referrer's code can call `decrement_referral` in a loop
and drive their count to 0, downgrading their discount tier. This is the exact
mirror of the count-*inflation* attack PR #1334 deliberately fixed with the
`referral_increments` dedup table — the deflation direction is now wide open,
and it directly contradicts the project rule *"New RPCs must define and enforce
a rate limit before merge — no unthrottled write endpoints."*

No client calls this RPC (grep: definition + design doc only), so removing
`EXECUTE` from `anon` would cost nothing today.

### `sql/first-referral-bonus.sql:47` — NEEDS-REVIEW (high)

**Commit:** `9c524212`

**Change summary:** `check_first_referral_bonus(p_code text)` — SECURITY
DEFINER; atomically sets `first_bonus_granted_at` and returns the referrer's
RevenueCat `rc_user_id` if eligible.

**Assessment:** Same exposure as above — anon-callable, no rate limit, no
device binding. Two consequences, both reachable by anyone holding a publicly
shared referral code:

1. **Bonus burn.** The function sets the claim flag *before* any entitlement is
   granted. An anon caller trips the flag, the Edge Function never runs, and the
   referrer silently loses their one-time free month. Not idempotent from the
   victim's perspective — it is single-use and consumable by a third party.
2. **Identifier disclosure.** It returns the referrer's RevenueCat
   `originalAppUserId` to an unauthenticated caller. `referralApi.js` now
   populates that column on every `generateServerCode`/`registerCode`
   (`getAppUserId()`, `purchases.js`), so the code→subscriber link is
   populated for real users. It is pseudonymous rather than name/email PII, but
   it is the handle used to address that subscriber in RevenueCat's API, and
   the project rule is explicit: *"API responses must not leak internal IDs."*

### `supabase/functions/first-referral-bonus/index.ts` — NEEDS-REVIEW (high)

**Commit:** `9c524212`

**Change summary:** New Supabase Edge Function granting a 1-month promotional
`safety_plus` entitlement via the RevenueCat REST API.

**Assessment:** Checked against the project's own "Edge function security" rule,
which requires edge functions to *"validate the `Authorization` header, enforce
the same rate limits as direct RPCs, never import the service-role key from
client-reachable code, and set `Content-Type` explicitly."* Three of four are
unmet:

- **No `Authorization` validation.** The function never reads the header, and is
  documented to deploy with `--no-verify-jwt`. `claimFirstReferralBonus()`
  (`referralApi.js:123`) sends `Bearer <VITE_SUPABASE_ANON_KEY>` — the public
  key from the client bundle. There is no authentication boundary.
- **No rate limiting.** Each call performs a DB round-trip and, when eligible, a
  RevenueCat write.
- **CORS `Access-Control-Allow-Origin: '*'`** on a write endpoint that grants a
  paid entitlement — the rule bans wildcard CORS on write endpoints.

Also note the failure path: on a non-2xx RevenueCat response the function
resets `first_bonus_granted_at` to `NULL` via a direct service-role table
update, clearing the claim flag with no dedup guard.

Service-role key handling is correct (server-side only, `Deno.env`), error
envelopes are generic (`db_error`, `internal`), and `Content-Type` is set
explicitly — those parts are fine.

**Not deployed.** CLAUDE.md records this function as BUILT, NOT DEPLOYED, and
the SQL migrations are run by hand in the Supabase SQL Editor. Static analysis
cannot confirm the live database's actual grant state — it is possible EXECUTE
was revoked out-of-band. Everything above describes what the committed SQL and
TypeScript produce if applied as written.

**Change summary:** `useFirstInbound(balance)` emits `FIRST_INBOUND_DETECTED`

For a coercion-resistant wallet whose threat model treats the backend as

**Commits:** `9c524212`, `41b48adc`

**Change summary:** Six new `SECURITY DEFINER` functions this window

### `src/lib/tracking-integration.jsx:29,50,64` — NEEDS-REVIEW (medium)

**Commit:** `41b48adc`

**Change summary:** `fireOnce()` writes its localStorage marker *before* calling
the emitter, and `useWalletReady()` calls `assignHoldout()` (another
localStorage write) before `safeEmit()`.

**Assessment:** The module header argues these hooks are "safe to mount
unconditionally" because `emit()`/`trackEvent()` suppress egress under
deniability/demo. That reasoning is correct for **egress** but does not cover
**local writes**, which happen unconditionally and ahead of every gate:

- `veyrnox-first-open-fired`
- `veyrnox-wallet-ready-fired`
- `veyrnox-first-inbound-fired`
- `veyrnox-holdout`

`WalletPortfolioPage` renders in decoy/duress sessions by design, so a decoy
session writes these to shared localStorage. Two effects:

1. **Deniability residue.** Persistent cross-session artifacts created by a
   decoy session — the same shape as C-1/K-2 from the 2026-07-20 audit, though
   materially milder: these keys are generic funnel markers and do not name
   duress/stealth/panic routes. `veyrnox-first-inbound-fired` is the notable
   one, since it asserts that funds were once received.
2. **Silent funnel loss.** A decoy session consumes the once-per-install flag,
   so the real session's `wallet_ready` / `first_inbound` never fires. Analytics
   would understate real activations with no signal that it happened — an I4
   fail-honest concern in the measurement itself.

`assignHoldout()` in a decoy session also fixes the notification holdout group
for the real user.

### `.github/workflows/deploy-preview.yml:39,55` — NEEDS-REVIEW (medium)

**Commit:** `fb6cdf0c` ci: staging environment with PR previews, E2E, and rollback (#1343)

**Change summary:** New Cloudflare Pages deploy workflow on `pull_request`,
`push: [main]`, and `workflow_dispatch`.

**Assessment:** Two supply-chain concerns:

- **`npm install --legacy-peer-deps` rather than `npm ci`** (also in
  `staging-e2e.yml:26`). `npm install` may resolve and write new versions at
  build time, defeating the lockfile pinning the project's dependency rule
  requires (*"Pin exact versions in `package-lock.json`"*). A deploy pipeline
  should install exactly the lockfile.
- **Deploy token in a job that builds PR-authored code.** The job runs
  `npm install` and `npm run build:staging` on the PR's tree, then hands the same
  job `secrets.CLOUDFLARE_API_TOKEN`. A PR touching a build script, postinstall
  hook, or Vite config executes attacker-controlled code alongside a live deploy
  token. The `pull_request` trigger (rather than `pull_request_target`) is the
  right choice and means **fork** PRs get no secrets — so exposure is limited to
  contributors with push access. Splitting build and deploy into separate jobs,
  passing only the `dist` artifact, would close it.

Separately, `push: [main]` runs the **production** build (`npm run build`, real
Supabase credentials) and deploys it to `--project-name=veyrnox-staging`. Given
that `.env.staging` blanks Supabase specifically so staging cannot write to
production, deploying a prod-credentialed build onto the staging project
partially undoes that intent. Worth confirming this is deliberate.

### `.github/workflows/rollback.yml:44,54` — NEEDS-REVIEW (low)

**Commit:** `fb6cdf0c`

**Change summary:** Manual rollback workflow with a `deployment_id`
`workflow_dispatch` input and a typed `confirm` gate.

**Assessment:** `${{ github.event.inputs.deployment_id }}` is interpolated
directly into the wrangler `command:` string and again into a `run:` shell block
in "Post summary" (inside backticks in an `echo`). The `run:` interpolation is a
genuine command-injection primitive — a crafted input containing backticks or
`$( )` executes in the runner. `workflow_dispatch` requires repo write access,
so the attacker must already be a collaborator, which caps severity — but the
project rule is unambiguous: *"never pass user input to ... template strings
that reach a shell."* Pass it via `env:` and reference `"$DEPLOYMENT_ID"`
quoted instead.

Also cosmetic-but-confusing: the workflow is titled "Rollback Production" and
its summary says "previous production deployment", while both steps target
`--project-name=veyrnox-staging`.

into `SendCrypto.jsx:814` ahead of `evaluateSendGate()`.

**Assessment:** Fails **open**. `isDeferred()` returns `false` from its `catch`
