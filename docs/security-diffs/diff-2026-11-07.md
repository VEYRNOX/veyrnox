### src/wallet-core/evm/replacement.js — SAFE (one NEEDS-REVIEW note below)
**Commit:** 04bdd9ee
**Change summary:** New module that re-reads a pending type-2 tx from the RPC, authenticates it, builds a same-nonce speed-up or a 0-value self-send cancel, and signs it only after step-up and a fresh pre-sign gate.
**Assessment:**
- I5: the RPC is treated as untrusted. The original is rebuilt with ethers, its hash recomputed against the requested hash, and its sender recovered from the signature (`authenticateOriginal`). Only the authenticated fields are used. Receipt absent, latest confirmed nonce not past the original nonce, and live chain id are all checked, and the review fingerprint is re-compared at sign time.
- I4: every failure path denies. `isReauthRequired` that is missing, throws or returns non-`false` gives `STEP_UP_REQUIRED`. The gate throwing or returning non-`true` gives `PRESIGN_BLOCKED`. `withPrivateKey` is reached only after both. The sign step re-validates the reviewed request (bump floor ≥ original +10%, ceiling, cancel shape, speed-up preserves every non-fee field).
- I3: `assertEgressAllowed()` is called at entry and after every `await` before the next RPC call or broadcast, and fails closed if `isDeniabilityOrDemoActive()` throws. The read-only reconcile poller also stops on a deniability/demo flip.
- Fee safety: live base fee above the per-network ceiling fails closed rather than being clamped. The tip is clamped, and the fee cap cannot be pushed above the ceiling.
- Honest messaging: `REPLACEMENT_BROADCAST_UNCERTAIN` and unknown errors are NOT in the pre-sign allowlist, so the UI cannot claim "nothing was signed" after a possible broadcast.
- I1: the private key exists only inside the `withPrivateKey` callback and is passed to `new Wallet(...)`. This is the already-recorded "EVM key unzeroable (ethers v6)" residual, not new.

### src/sign-gate/presignOrReject.js — NEEDS-REVIEW (design note, not a defect)
**Commit:** 04bdd9ee
**Change summary:** New shared async gate: takes a fresh RASP sample, then runs the same pure `presignGate`. Missing artifact, thrown error or unexpected shape all return BLOCKED.
**Assessment:** Fail-closed as required (`artifact?.tier ?? TIER.BLOCK`, `catch` returns BLOCKED, only `proceedAllowed === true` passes). It passes `txLevel = LEVEL.OK` and `acknowledged = false`, so a WARN/CONFIRM RASP tier blocks the replacement outright with no "sign anyway" path. That is the safe direction, and the comment states it. Two consequences a reviewer should know:
1. Replacements get **no transaction-risk (Vigil/simulation) screening**, since the level is hard-coded OK. Defensible, because a speed-up re-sends an already-signed payment and a cancel sends 0 to self, and it avoids a new `tip-screen` egress (I2). But a tx that was risky at original send time is not re-evaluated.
2. A user on a rooted/WARN-tier device can send normally with acknowledgement but cannot speed up or cancel. This is an availability trade-off, not a security regression.

### src/pages/TransactionHistory.jsx — SAFE (low-severity observation)
**Commit:** 04bdd9ee
**Change summary:** Adds Speed up / Cancel buttons on pending EVM sends, a review dialog, an in-page step-up (PIN/password re-entry with a 5-attempt cap that locks the wallet), 2FA via `useActionGuard`, and local-history persistence of the replacement row.
**Assessment:**
- Controls hidden when `DEMO || denySession`. The prepare mutation re-checks `DEMO || isDeniabilityOrDemoActive()`. The history write is skipped in a deniability session.
- Step-up mirrors `SendCrypto`: wrong credentials count toward the cap even if the dialog is dismissed (no dodging the cap), verifier-unavailable/bricked results fail closed, and a generation counter invalidates any in-flight check or 2FA continuation once the review is dismissed or unmounted. A double-submit is blocked by `replacementInFlightRef`.
- Persistence is best-effort after broadcast, so a storage error cannot invite a duplicate replacement. The original row stays `pending` until a receipt decides, and the UI hides controls on any hash that already has a pending replacement.
- **Observation (LOW, unverified):** `trackReplacementOutcome` polls for up to ~20 min (80 × 15 s) after broadcast. It stops on deniability/demo, but nothing in the visible code stops it on wallet lock or panic wipe, and it then calls `base44.entities.Transaction.update(id, …)` for rows that a wipe may have removed. I did not verify how `update` behaves on a missing id, so this is recorded as something to confirm, not a finding. Reads are public-chain RPC calls only; nothing is broadcast from the poller.
- New persisted fields on the local Transaction row (`replaces_tx_hash`, `replacement_action`, `from_address`, `network`) live in the existing Transaction entity store. No new localStorage key is introduced, so `ALL_RESIDUE_KEYS` is not implicated.
