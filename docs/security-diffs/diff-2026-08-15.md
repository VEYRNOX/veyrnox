### ios/App/CapApp-SPM/Sources/CapApp-SPM/FirebaseObservability.swift + android/app/build.gradle — NEEDS-REVIEW
**Commit:** `bac1cb30` ci(firebase): trim to Spark free tier (#1755) (with earlier Firebase wiring in the same window)
**Tracking:** [#1771](https://github.com/VEYRNOX/veyrnox/issues/1771) — **REMEDIATION IN FLIGHT, see Remediation section below.** Owner decided Test Lab-only on both platforms; PRs #1782 (Gaps 1+2) and #1784 (Gap 3) were open at time of writing.

**Change summary:** Firebase Crashlytics and Firebase Performance are added as
unconditional dependencies of both the iOS SPM target (`firebase-ios-sdk`, exact
`12.12.1`) and the Android app module (`firebase-bom:34.16.0`, `firebase-crashlytics`,
`firebase-perf`). Runtime collection is gated: Android via
`FIREBASE_OBSERVABILITY_ENABLED` (Gradle property, defaults `false`) plus manifest
placeholders; iOS via an Info.plist flag `VeyrnoxFirebaseObservabilityEnabled`
(`$(VEYRNOX_FIREBASE_OBSERVABILITY)`, empty in production) OR a
`--firebase-observability-smoke` launch argument, AND the presence of
`GoogleService-Info.plist`. No Analytics product is included on either platform.

**Assessment:** The gates themselves are fail-closed and correctly built. Android's
`(project.findProperty('FIREBASE_OBSERVABILITY_ENABLED') ?: 'false').toBoolean()` defaults
off, the `google-services` / crashlytics / perf plugins apply only when
`google-services.json` exists, and the Firebase Test Lab variant is a separate
`applicationIdSuffix ".firebase.testlab"` build with `bundleFirebaseTest` disabled and a
signing-fingerprint guard. iOS returns early on an empty flag and again on a missing
config file. That much is sound engineering. Three things still need an owner decision:

1. **No test asserts production is actually clean.** `src/__tests__/firebase-observability.test.js`
   is a structural string test — it asserts that certain literals exist in
   `build.gradle`, `Package.swift`, `ci.yml`, etc. It never asserts that a production
   release build yields `FIREBASE_OBSERVABILITY_ENABLED=false`, that a production AAB
   ships without `google-services.json`, or that the production iOS archive lacks
   `GoogleService-Info.plist`. On a repo whose release-cert guard regressed four times
   and where a test was once edited to assert a bug, a string test is thin protection
   for an I2 boundary. The assertion that matters — "the shipped production artifact
   cannot talk to Google" — is currently a code comment, not a check.

2. **Staging builds egress outside the app's own consent and deniability model.**
   `publish-ios-staging` sets `VEYRNOX_FIREBASE_OBSERVABILITY=YES` and fetches a real
   config; Android staging store packages take the same path. Those builds are installed
   by real testers via TestFlight and Play internal testing — and the mandatory
   1.0.1 pre-submission checklist requires exactly that. Crashlytics and Performance are
   native-layer SDKs: they do not consult `lib/consent.js`, and they do not know
   `isDeniabilityOrDemoActive()` exists. So on a staging build, a crash or a performance
   trace occurring **during a decoy/duress session** still transmits to Google. That is an
   I3 concern ("deniability mode → zero backend calls"), scoped to staging/Test Lab
   artifacts only — it does not affect production as currently gated. Given that
   deniability features are precisely what gets exercised on those test devices, this is
   worth an explicit decision rather than an implicit one.

3. **Android uses the re-enableable kill switch, not the permanent one.** The manifest
   sets `firebase_performance_collection_enabled` / `firebase_crashlytics_collection_enabled`
   to the placeholder value. For Performance, `..._enabled=false` can be flipped back on at
   runtime via `setPerformanceCollectionEnabled(true)`; `firebase_performance_collection_deactivated=true`
   cannot. For a production wallet build the permanent form is the stronger posture.

Not rated REGRESSION: nothing here is currently wired to egress from a production build,
and the gating is real. Rated NEEDS-REVIEW because a Google telemetry SDK now lives inside
the process that holds private keys, the "production is clean" claim is asserted rather
than tested, and the staging path bypasses the consent chokepoint the project built for
exactly this purpose.

### src/wallet-core/shardBackup.js:309–320 — NEEDS-REVIEW (low)
**Commit:** `6e38c53b` fix(shard-backup): canonical hashVault, bump SHARD_BUNDLE_VERSION 1→2 (#1753)
**Tracking:** [#1772](https://github.com/VEYRNOX/veyrnox/issues/1772) — **RESOLVED, see Remediation section below.** Claim confirmed, legacy path deleted in #1778 (`c647829f`).

**Change summary:** Fixes a real bug — `JSON.stringify(vault, Object.keys(vault).sort())`
applies its array replacer as a key *filter at every nesting level*, so nested objects
such as `vault.kdf` serialised to `'{}'` and changes inside them were invisible to the
integrity hash. Replaced with a recursive `canonicalStringify`, bumping
`SHARD_BUNDLE_VERSION` 1→2. `decodeShareBundle` continues to accept `v:1` and verifies
those with the retained `legacyHashVault`.

**Assessment:** The fix is correct and the version bump is right. The concern is the
retained legacy branch. `decodeShareBundle` accepts a `v:1` bundle and validates it with
the exact hasher whose nested-object blindness was just fixed, so a `v:1` bundle can carry
arbitrary tampering in any nested `vault.*` field and still pass the integrity check. The
code comment states no v1 bundles exist in production (Phase 1, pre-audit) — which means
the compatibility branch is being kept for zero real artifacts while reopening the
weakness for anyone who can hand the user a file. Impact is bounded: the vault payload is
AES-GCM, `vaultHash` is an integrity aid rather than an authenticity control, and
tampering `vault.kdf` produces a decryption failure rather than disclosure. Recommend
dropping the `LEGACY_SHARD_BUNDLE_VERSION` acceptance path outright given the stated
absence of v1 bundles; if it must stay, it should carry an expiry.
