### ios/App/CapApp-SPM/Sources/CapApp-SPM/FirebaseObservability.swift + android/app/build.gradle — NEEDS-REVIEW
**Commit:** `bac1cb30` ci(firebase): trim to Spark free tier (#1755) (with earlier Firebase wiring in the same window)
**Tracking:** [#1771](https://github.com/VEYRNOX/veyrnox/issues/1771) — owner decision requested on all three gaps below

**Change summary:** Firebase Crashlytics and Firebase Performance are added as
unconditional dependencies of both the iOS SPM target (`firebase-ios-sdk`, exact
`12.12.1`) and the Android app module (`firebase-bom:34.16.0`, `firebase-crashlytics`,
`firebase-perf`). Runtime collection is gated: Android via
`FIREBASE_OBSERVABILITY_ENABLED` (Gradle property, defaults `false`) plus manifest
placeholders; iOS via an Info.plist flag `VeyrnoxFirebaseObservabilityEnabled`
(`$(VEYRNOX_FIREBASE_OBSERVABILITY)`, empty in production) OR a
`--firebase-observability-smoke` launch argument, AND the presence of
`GoogleService-Info.plist`. No Analytics product is included on either platform.

**Assessment:** The gates themselves are fail-closed and correctly built. Android's
`(project.findProperty('FIREBASE_OBSERVABILITY_ENABLED') ?: 'false').toBoolean()` defaults
off, the `google-services` / crashlytics / perf plugins apply only when
`google-services.json` exists, and the Firebase Test Lab variant is a separate
`applicationIdSuffix ".firebase.testlab"` build with `bundleFirebaseTest` disabled and a
signing-fingerprint guard. iOS returns early on an empty flag and again on a missing
config file. That much is sound engineering. Three things still need an owner decision:

1. **No test asserts production is actually clean.** `src/__tests__/firebase-observability.test.js`
   is a structural string test — it asserts that certain literals exist in
   `build.gradle`, `Package.swift`, `ci.yml`, etc. It never asserts that a production
   release build yields `FIREBASE_OBSERVABILITY_ENABLED=false`, that a production AAB
   ships without `google-services.json`, or that the production iOS archive lacks
   `GoogleService-Info.plist`. On a repo whose release-cert guard regressed four times
   and where a test was once edited to assert a bug, a string test is thin protection
   for an I2 boundary. The assertion that matters — "the shipped production artifact
   cannot talk to Google" — is currently a code comment, not a check.

2. **Staging builds egress outside the app's own consent and deniability model.**
   `publish-ios-staging` sets `VEYRNOX_FIREBASE_OBSERVABILITY=YES` and fetches a real
   config; Android staging store packages take the same path. Those builds are installed
   by real testers via TestFlight and Play internal testing — and the mandatory
   1.0.1 pre-submission checklist requires exactly that. Crashlytics and Performance are
   native-layer SDKs: they do not consult `lib/consent.js`, and they do not know
   `isDeniabilityOrDemoActive()` exists. So on a staging build, a crash or a performance
   trace occurring **during a decoy/duress session** still transmits to Google. That is an
   I3 concern ("deniability mode → zero backend calls"), scoped to staging/Test Lab
   artifacts only — it does not affect production as currently gated. Given that
   deniability features are precisely what gets exercised on those test devices, this is
   worth an explicit decision rather than an implicit one.

3. **Android uses the re-enableable kill switch, not the permanent one.** The manifest
   sets `firebase_performance_collection_enabled` / `firebase_crashlytics_collection_enabled`
   to the placeholder value. For Performance, `..._enabled=false` can be flipped back on at
   runtime via `setPerformanceCollectionEnabled(true)`; `firebase_performance_collection_deactivated=true`
   cannot. For a production wallet build the permanent form is the stronger posture.

Not rated REGRESSION: nothing here is currently wired to egress from a production build,
and the gating is real. Rated NEEDS-REVIEW because a Google telemetry SDK now lives inside
the process that holds private keys, the "production is clean" claim is asserted rather
than tested, and the staging path bypasses the consent chokepoint the project built for
exactly this purpose.

### src/wallet-core/shardBackup.js:309–320 — NEEDS-REVIEW (low)
**Commit:** `6e38c53b` fix(shard-backup): canonical hashVault, bump SHARD_BUNDLE_VERSION 1→2 (#1753)
**Tracking:** [#1772](https://github.com/VEYRNOX/veyrnox/issues/1772) — owner to confirm the "no v1 bundles exist" claim, then delete the legacy path

**Change summary:** Fixes a real bug — `JSON.stringify(vault, Object.keys(vault).sort())`
applies its array replacer as a key *filter at every nesting level*, so nested objects
such as `vault.kdf` serialised to `'{}'` and changes inside them were invisible to the
integrity hash. Replaced with a recursive `canonicalStringify`, bumping
`SHARD_BUNDLE_VERSION` 1→2. `decodeShareBundle` continues to accept `v:1` and verifies
those with the retained `legacyHashVault`.

**Assessment:** The fix is correct and the version bump is right. The concern is the
retained legacy branch. `decodeShareBundle` accepts a `v:1` bundle and validates it with
the exact hasher whose nested-object blindness was just fixed, so a `v:1` bundle can carry
arbitrary tampering in any nested `vault.*` field and still pass the integrity check. The
code comment states no v1 bundles exist in production (Phase 1, pre-audit) — which means
the compatibility branch is being kept for zero real artifacts while reopening the
weakness for anyone who can hand the user a file. Impact is bounded: the vault payload is
AES-GCM, `vaultHash` is an integrity aid rather than an authenticity control, and
tampering `vault.kdf` produces a decryption failure rather than disclosure. Recommend
dropping the `LEGACY_SHARD_BUNDLE_VERSION` acceptance path outright given the stated
absence of v1 bundles; if it must stay, it should carry an expiry.

### src/lib/useKekEnrollmentGate.js:22–37 — NEEDS-REVIEW (low, structural)
**Commit:** `dface8d8` fix(kek): persist insecure-tier verdict to end enrollment loop on StrongBox-less devices (#1760), with `de6e34df` (#1763) adding the second writer
**Tracking:** [#1773](https://github.com/VEYRNOX/veyrnox/issues/1773) — carries the `lib/consent.js` remediation patch; NOT a live defect, see below

**Change summary:** Introduces a new shared-localStorage key `veyrnox-kek-insecure-tier`
so a device that fails the hardware-tier gate is not re-prompted on every unlock. Two
writers: `persistKekInsecureTier()` (internal, called from `enroll()`) and
`clearKekInsecureTier()` (exported, called from `HardwareKekSettings.jsx`). Correctly
added to `METADATA_RESIDUE_KEYS` in `panic.js` in the same window.

**Assessment: not currently exploitable — verified, not assumed.** I checked both paths.
The detect effect returns early on `isDeniabilityOrDemoActive()`, so the gate never
activates in a decoy session and `enroll()` is unreachable there. The second writer is
inside the `{isNative && enrolled === false && !blocked && (...)}` branch at
`HardwareKekSettings.jsx:544`, where `blocked = isDecoy || isHidden` (line 351) — so the
banner does not render and `clearKekInsecureTier()` cannot fire in a decoy/hidden session.
No I3 violation today.

The structural note stands regardless. Neither write function carries its own
`isDeniabilityOrDemoActive()` check; the module comment justifies their absence by
pointing at the detect effect's early return — a guard in a *different function* from the
one doing the write. This is precisely the shape recorded for the telemetry-consent bug:
three writers to a shared key, the guard duplicated at call sites, and the third writer
shipping unguarded. The remediation pattern already exists in this codebase —
`lib/consent.js` gates inside `setConsent()`/`clearConsent()` and leaves reads ungated —
and applying it here is two lines. Panic-wipe coverage was handled correctly, which is the
half that has historically been missed; this is the other half.

## Controls ADDED this window (all SAFE)

- **Native RASP gates on both Enclave plugins** (`#1759`, `#1765`) — Android
  `VeyrnoxEnclavePlugin.createWrappingKey/wrap/unwrap` and iOS
  `VeyrnoxEnclavePlugin` + `HardwareKekPlugin.enroll/getHardwareFactor` now reject at
  BLOCK tier at the native layer. Closes a path where in-page injected JS on a hooked
  device could reach `Capacitor.Plugins.*`, satisfy biometry, and obtain the plaintext
  vault blob or the raw hardware factor H. This is the highest-value addition in the window.
- **RASP probe canary** (`#1758`) — every detection helper on both platforms swallowed
  exceptions to `false`, so a Frida gadget hooking a common primitive produced a
  fabricated CLEAN verdict. Three primitives are now called *without* the swallow; a
  throw rejects the call and maps to `INTEGRITY_UNAVAILABLE` (WARN/BLOCK). Regression
  test added in `src/rasp/__tests__/nativeProbe.test.js`.
- **I3 gates on all `/api/data/*` helpers** (`#1768`) — `fetchPrices`, `fetchKlines`,
  `fetchCoinGecko`, `fetchGasFees`, `fetchNews` gained `i3Guard()`; previously only
  `fetchOkxCandles` had it and the others relied on react-query `enabled: !decoy` at the
  UI layer. Module-level chokepoint now authoritative.
- **Buy-URL origin assertion** (`#1768`) — `createBuySession` throws
  `BUY_URL_UNTRUSTED_ORIGIN` unless the returned URL host is `global.transak.com` or
  `global-stg.transak.com`, closing an in-app phishing surface via a compromised or
  misrouting edge function.
- **Transak postMessage origin check + `/buy` route gate** (`#1762`) — spoofed
  `TRANSAK_ORDER_SUCCESSFUL` from any frame is rejected; direct navigation to `/buy` on a
  build where `VITE_BUY_ENABLED !== 'true'` is now suppressed via `useBuyEnabled()`.
- **SecurityCenter decoy query gates** (`#1762`) — two react-query calls that ran
  unconditionally even in decoy/hidden sessions now carry `enabled: !deniable`, matching
  the page's own stated contract.
- **SendCrypto shared-localStorage write gates** (`#1762`) — two toggles no longer
  persist from a decoy/hidden session; in-memory state still updates.
- **WalletConnect proposal expiry re-check** (`#1757`) — `approveSession` now re-checks
  the proposal's own `expiryTimestamp`, not just the 5-minute insertion TTL, and evicts +
  throws. Paired with `SessionProposalModal` dropping a dead "acknowledge and connect"
  checkbox that could never work, since `approveSession` unconditionally throws
  `DAPP_BLOCKED_KNOWN_BAD` for flagged domains — UI now matches the authoritative handler.
- **Genuine hardware-tier capability probe** (`#1763`) — `isSecureHardwareAvailable()`
  replaced a `BiometricAuth.checkBiometry().deviceIsSecure` proxy with
  `isEligibleHardwareCapability()`, requiring an enrolled biometric AND a real backing
  tier (`secureEnclave` / `strongBox` / `tee`). Android derives this from a disposable
  probe alias's `KeyInfo` and deletes it in a `finally`.
- **M2c→M2b downgrade surfaced honestly** (`#1756`) — `_reapplyEnclaveWrapIfNeeded` now
  returns a status instead of `undefined`, `restoreFromPersonalBackupShares` returns
  `{ downgradedFromEnclave }`, and `RestoreFromShares` renders a warning toast rather than
  a success toast when the outer Enclave wrap could not be re-applied. Web returns the
  same shape for platform-agnostic callers. Textbook I4.
- **Canonical shard-bundle hasher** (`#1753`) — see F-2 above; the fix itself is correct.
- **Passphrase wrap actually wired** (`#1752`) — the "Encrypt one share with a passphrase"
  checkbox previously wired UI state that was never consumed, so the export was always raw.
  Now backed by `wrapBundleWithPassphrase` under a distinct `recovery-bundle-v1` envelope
  type with its own AAD binding, non-cross-parseable with the share-only wrap.
- **`getPersistedVault` forwarded on the native facade** (`#1754`) — a missing forwarder
  made every native "Split & save 3 shares" throw.
- **Byte-accurate body caps on four edge functions** (`#1761`).
- **CI privilege reduction** (`#1764`) — `deploy-preview.yml` drops
  `pull-requests: write` + `deployments: write` from the workflow level (the `deploy` job
