   Moving the tier check to sit *after* the `localHit` branch would preserve the

### src/wallet-core/__tests__/shamir.test.js:281 — NEEDS-REVIEW
**Commit:** `bf233155` test(shamir): make inconsistent-share check deterministic
**Change summary:** The "rejects an inconsistent extra share" test stopped
building its Frankenstein share from a second `split()` (copying the whole
y-vector from a different polynomial) and now flips one bit —
`franken[Y_START] ^= 0x01` — recomputing the CRC as before.

**Assessment:** The new test is valid and still exercises the control: a
single-byte y mutation with an intact commitment and a recomputed CRC is
inconsistent with the polynomial interpolated from the two good shares, so
`combine()` must reject it. Determinism is a real improvement over a
randomised fixture. The assertion was not weakened or removed.

The **stated rationale** is what needs review. The comment says a second random
split "can occasionally produce the same polynomial, leaving the purportedly
inconsistent share intact". With `k=2` the polynomial is degree 1 and each of the
32 secret bytes carries its own GF(256) coefficient drawn from
`crypto.getRandomValues` (`shamir.js:30`, `:289`). Two independent splits
colliding on all 32 coefficients is ~2⁻²⁵⁶. That is not an "occasional" flake by
any margin.

So either the rationale is post-hoc and the change is a harmless
determinism refactor, or a flake really was observed in a wallet-core crypto test
and its actual cause has not been identified — and the fix removed the symptom.
The second reading is the one worth ten minutes: the plausible non-negligible
causes all live in `splitRaw`'s coefficient generation or x-coordinate
assignment, which is the library-swap surface tracked in
`docs/audit-triage/shamir-library-swap-design-2026-08-19.md`. Nothing here is
evidence of a defect; it is evidence that a stated reason does not survive
arithmetic, in the one module where that matters most.

### android/app/src/main/java/com/veyrnox/app/HuaweiReceiptVerifier.kt — SAFE (control ADDED)
**Commit:** `307fd598` fix(huawei): verify HMS IAP receipt signatures before granting entitlement (#2191)
**Change summary:** New `SHA256withRSA` verifier over the raw HMS purchase JSON
against the AppGallery Connect public key, wired into both receipt sinks in
`HuaweiIapPlugin.kt` — the post-purchase `handleOnActivityResult` path and the
`obtainOwnedPurchases` restore path.

**Assessment:** Real control where there was none: before this, `safety_plus` and
`ai_security_protection` were granted from an unverified receipt on the huawei
flavor. Fail-closed in every direction — null/blank data, signature or key all
return false; `runCatching { … }.getOrDefault(false)` swallows nothing into a
pass. `BuildConfig.HUAWEI_IAP_PUBLIC_KEY` defaults to `""`, so an unconfigured
build grants nothing rather than trusting everything, and
`android/app/build.gradle:309-341` hard-fails a huawei **release** build on a
blank or unparseable key — the guard parses the key with `KeyFactory` exactly as
the app will, so a mispaste fails at build time rather than on every customer's
device.

Two details verified rather than assumed:
- The restore path pairs `inAppSignature` to `inAppPurchaseDataList` **by index**
  and drops anything whose signature is absent at that index
  (`forEachIndexed` + `getOrNull`), which is the HMS contract. An unpaired entry
  is dropped, not passed through.
- `update(purchaseData.toByteArray(UTF_8))` verifies the bytes as received with
  no re-serialisation, so key order or whitespace normalisation cannot break a
  legitimate signature.

The KDoc states the honest ceiling out loud — an attacker who can patch the APK
or hook HMS Core can substitute the key, and only server-side verification
against Huawei's order service removes the class. That is the correct framing and
should not be softened. The verifier lives in the shared `main` source set so
the existing JVM unit-test job covers it; `HuaweiReceiptVerifierTest.kt` (124
lines) uses real RSA keys and attack vectors rather than mocks.

**Minor, not a finding:** `buildConfigField "String", "HUAWEI_IAP_PUBLIC_KEY",
"\"${project.findProperty(...) ?: ''}\""` interpolates the property into
generated Java source without escaping. A base64 X.509 key cannot contain `"` or
`\`, so no real value breaks it — but the attacker who would exploit it is
whoever invokes the build, i.e. nobody the threat model covers. Noted so the
pattern is not copied to a field that *can* carry arbitrary text.
