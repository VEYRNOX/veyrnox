### src/lib/tracking-integration.jsx:424 — REGRESSION
**Commit:** 61b8338f feat: WIN paywall with AI Security upsell, Vigil owl on the backup nag, 7-day dormancy reminder (#2661)
**Change summary:** `armDormancyReminder()` cancels, then reschedules, a single `LocalNotifications` entry (id 9005) 7 days out. `WalletProvider` calls it on both unlock paths. Arming is suppressed in decoy/demo sessions; cancelling is not suppressed.
**Assessment:** The decoy-session asymmetry is handled correctly and is documented well: a decoy unlock cancels the reminder and never arms it. The panic path is missing. I checked every reference from `origin/main`:
- `git grep` finds no `LocalNotifications.cancel` and no `cancelDormancyReminder(` call in `src/wallet-core/**`. The source comment itself lists `cancelDormancyReminder` as "NOT WIRED".
- The lock-time sweep in `hooks/usePriceAlertNotifier.js` (the Codex P2 2026-08-16 fix, which runs on every `APP_LOCK_EVENT` including panic) cancels only the price-alert ids it tracks and removes *delivered* notifications. It does not cancel *pending* id 9005.

So a pending OS notification survives a panic wipe and fires later. The source comment says "no new localStorage key, so no new panic-wipe residue". That reasoning is the one `CLAUDE.md` warns against: what makes something a tell is its *presence*, and a scheduled OS notification is present in the same way a leftover key is (same class as #1415). It also outlives the app session, which localStorage residue does not.

Suggested fix: call `cancelDormancyReminder()`, or cancel id 9005 directly, in the panic-wipe path, and add a regression test that fails if panic runs without cancelling 9005. Found by static analysis only, not device-verified.

The open question is the threat model, not this diff. Theft Protection's send-side check now depends on a spend limit that can be **edited upward, disabled or deleted with no step-up**. `addLimit`, `toggleLimit` and `deleteLimit` do not go through `requireTwoFactor`; only session revocation does (`useActionGuard` at `SecurityCenter.jsx:45`). Someone holding an unlocked phone, which is exactly the thief case, can raise or remove the cap with a single confirmation and then send with no biometric check. `CLAUDE.md` lists "spend-limit changes" among the high-risk operations that require step-up re-auth.

This gap existed before the window, but #2680 turned this limit into the mechanism Theft Protection relies on, and #2682 adds a third ungated way to loosen it (edit). Suggestion: guard *loosening* changes (raise, disable, delete) with `requireTwoFactor` or the Theft Protection biometric check, and leave tightening changes ungated.
