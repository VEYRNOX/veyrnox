### `android/app/src/main/java/com/veyrnox/app/OtaBundleVerifier.kt:165` + `OtaUpdatePlugin.kt:149` — SAFE
**Commit:** 3481ac51 fix(android): OTA prepare downloads files the APK dropped instead of aborting (#2816)
**Change summary:** The `prepare()` pre-fill loop moved into a pure `OtaBundleVerifier.prefill`.
A held file whose embedded asset cannot be opened (Android drops `.well-known/*` from APK assets)
is now returned as `missing` and downloaded, where before it threw `OTA_IO` and failed every
Android update.
**Assessment:** I read both files in full on `origin/main`, not just the diff. The change widens
nothing in the trust boundary:
- `prepare()` still calls `readVerifiedManifest` (ECDSA P-256 over the manifest bytes against the
  two pinned YubiKey SPKIs, then channel, version and `minNativeApi`) **before** `prefill` runs.
  So the `files` map that drives the copy and the download list is signed. Every path in it
  passes `isSafePath`, which rejects `..` and `.` segments, so `File(dir, path)` cannot escape
  the staging dir.
- Nothing is trusted on the strength of `prepare()`. `stage()` calls `isValid`, which re-checks
  the signature and runs `verifyFiles`. That function requires the on-disk file set to be
  **exactly** the manifest key set, and every file to match its sha256. A downloaded replacement
  for a missing asset is held to the same rule as a copied one. The `mkdirs()` call can leave an
  empty directory behind, but `verifyFiles` counts files only, so that cannot add an
  unauthorised file.
- Only the asset-open `IOException` became "missing". A failure while copying a source that did
  open still throws, and the result is still `OTA_IO`, so it fails closed.
- Pinned by `OtaBundleVerifierTest.kt` (+51 lines, new tests only, nothing removed). The
  "reintroduce the throw, two go red" claim in the docs was not re-run here.
Status in the docs is honest: "Verified on the emulator", "Not yet verified on a physical phone",
and "not in 1.0.2" (every shipped Android binary still fails closed and stays on its embedded
bundle).

### `scripts/ota/verify-live.mjs` (new), `scripts/ota/manifest.mjs:31` — SAFE
**Commits:** a51d1707 (#2807), e59120a3 (#2817)
**Change summary:** A release-operator script that fetches every object back from
`updates.veyrnox.com` and compares it with the sealed local release. It checks the manifest and
signature byte for byte and every file by sha256. Each object is requested a second time with
Android's `Accept`/`User-Agent`. `manifest.mjs` only exports `SAFE_PATH`.
**Assessment:** I read the script in full. It runs on the operator's machine, not on a device,
and only reads. It is https-only (http allowed only for localhost), refuses a base URL that
carries credentials, and refuses unsafe manifest paths before building URLs. It treats a 4xx as
final and exits 1 on any mismatch. It gates the `latest.json` upload, which is a supply-chain
control in the right place. It cannot weaken device-side verification, which stays the
authority. Covered by `ota-verify-live.test.js` (+242 lines, new).

## Observations (not findings)

- **O-1: OTA is now a live remote-code path on production iOS.** A signed no-change canary is on
  the production channel, so iOS 1.0.2 installs that pass the native checks will boot web code
  that did not come from the store binary. The controls are sound as built: pinned offline P-256
  keys on two hardware tokens, a signed manifest, per-file sha256 with an exact file set, a
  version floor, and a channel check. The doc states the gaps itself: attestation does not cover
  OTA code, "ready" is a first-render heuristic, and no physical device has verified it. OTA is
  not named in the §24 audit-gate list in `CLAUDE.md`. **Recommend explicitly including the OTA
  loader (iOS and Android native verifier, `src/lib/otaUpdate.js`, the signing procedure) in the
  scope of the outstanding independent audit.** This is a scope note for the owner, not a
  regression.
- **O-2: Cloudflare `updates.veyrnox.com` hardening is procedural, not configured.** Response
  rewriting (Email Obfuscation, Web Analytics injection) is avoided by uploading every object as
  `application/octet-stream` and by running `verify-live`. No zone configuration rule disables
  rewriting for the host. Any failure fails closed (the update never installs), so this is an
  availability risk only.
