### `sql/check-first-referral-bonus-hardening.sql` — RESOLVED (was NEEDS-REVIEW high)

**Commit:** `13844f3e` (#1351)

Both defects closed. EXECUTE revoked from PUBLIC/anon/authenticated and granted
to service_role, which ends both the bonus-burn and the `rc_user_id` disclosure
to unauthenticated callers. The claim collapses to a single statement —

```sql
UPDATE public.referrals r SET first_bonus_granted_at = now()
 WHERE r.code = p_code AND r.first_bonus_granted_at IS NULL
   AND EXISTS (…paid attribution…)
RETURNING r.rc_user_id INTO v_rc_user_id;
```

— so `RETURNING` yields a row only to the caller whose UPDATE actually flipped
the flag. The previous SELECT-then-UPDATE-then-unconditional-RETURN could hand
`rc_user_id` to both racers and grant two free months for a one-time bonus.
`search_path` pinned to `''`.

The file also corrects `sql/first-referral-bonus.sql`'s header, which had
claimed "atomic" and "idempotent" of code that was neither, and marks that block
`!! SUPERSEDED` with a warning that re-running it silently reverts the hardened
body and drops the pin (CREATE OR REPLACE preserves privileges but not
attributes — a genuinely non-obvious failure mode, and correctly flagged).

### `sql/definer-search-path-pin.sql` — RESOLVED (was NEEDS-REVIEW medium)

**Commit:** `559a58fb` (#1352)

Catalog-driven rather than eight hardcoded `ALTER`s: it loops over
`pg_proc WHERE prosecdef AND NOT EXISTS (proconfig LIKE 'search_path=%')` and
pins each. Two details that make this better than the obvious implementation —

- It builds signatures with `format('%I.%I(%s)', …)` plus
  `pg_get_function_identity_arguments`, not `oid::regprocedure`, because
  regprocedure omits the schema when the function is search_path-visible — which
  would emit an ALTER that re-resolves through the very mechanism being fixed.
- It **skips already-pinned functions**, so it cannot downgrade
  `decrement_referral` / `check_first_referral_bonus` from the stricter
  `search_path = ''` to the looser `public, extensions, pg_temp`.

A second `DO` block re-runs the predicate and `RAISE EXCEPTION`s if anything is
still unpinned. The SQL Editor runs the script as one transaction, so a partial
pin rolls back rather than being mistaken for a complete one (I4).

### `sql/referrals-select-lockdown.sql` + base schema files — RESOLVED (new class, well found)

**Commits:** `3095f0ac` (#1361), `a7e43fac` (#1364), `d9261d2c` (#1365)

### 1. rollback.yml command injection — **RESOLVED** (`34f5da31`, PR #1398)

Landed after the scan window closed at `183ec34c`, so the scan could not have
seen it. Verified from the merged state of `main`, not from the PR description:

- **No raw input reaches any `run:` block.** `git show origin/main:` on the
  workflow leaves exactly three `github.event.inputs` references: two `if:`
  job-level expression comparisons (not shell contexts) and one `env:`
  assignment, which is the fix.
- A new `Validate deployment id` step (`id: dep`) takes the raw value via
  `env: RAW_DEPLOYMENT_ID`, strips whitespace, and matches it against an
  anchored UUID pattern. Both the wrangler `command:` and the `Post summary`
  step now read `steps.dep.outputs.id`.
- `Post summary` also passes `github.actor` via `env:` and quotes both
  variables.

**Validation deliberately differs from `deploy-preview.yml`.** That workflow
sanitises by substitution (`tr -c 'a-zA-Z0-9-' '-'`), which is right for a
branch name — it legitimately contains `/` and only has to survive as a label.
A deployment ID is an exact identifier, so rewriting a character silently
yields a *different well-formed ID* and would roll back to the wrong
deployment. The fix validates and rejects instead, failing closed (I4). Blank
still means "previous deployment", the documented path. The structural half —
raw value through `env:` only, downstream steps reading a workflow-produced
value — is identical to `deploy-preview.yml`, and is the part that closes the
injection.

The fix's shell logic was exercised against 9 inputs (blank, valid, uppercase,
whitespace-padded, and 5 injection payloads: backtick, `$( )`, command-chain
appended to a valid UUID, newline-embedded, and a plausible short ID) with a
canary file. All 5 payloads rejected; canary never created. That is a unit
exercise of the step's script, **not** a dispatch of the workflow itself.

Also in that PR, and worth recording because the report flagged it as
cosmetic: the workflow was renamed **"Rollback Production" → "Rollback
Staging"**. Both its steps target `--project-name=veyrnox-staging`, and
`veyrnox-staging` is the only Cloudflare Pages project this repo deploys to —
so the old title was wrong in a way that would only surface mid-incident.

### 2. tracking-integration deniability writes — **NOT RESOLVED ON `main`**

A fix exists in **open PR #1399** (`fix/tracking-deniability-writes`). It has
**not merged** — auto-merge is armed and the PR was `BLOCKED` on pending
checks when this amendment was written. Confirmed against `origin/main` at
`34f5da31`: `src/lib/tracking-integration.jsx` contains no `suppressed()` and
no `isDeniabilityOrDemoActive` reference. **The finding above stands on `main`
as of this amendment**, and nothing here should be read as closing it.

Recorded now, ahead of the merge, so this log does not imply a fix is live
before it is. What the PR does, for when it lands:

- Gates `fireOnce()` on `DEMO || isDeniabilityOrDemoActive()` — the same
  predicate shape `api/trackEvent.js` uses — placed **before the read**, so a
  decoy session neither writes the marker (residue) nor consumes it (funnel
  theft). `assignHoldout()` is covered transitively, running inside
  `useWalletReady`'s `fireOnce` callback.
- Routes `useFirstInbound` through `fireOnce()`. It had its own near-identical
  inline localStorage path, which is why gating `fireOnce` alone would have
  missed that one marker.
- Gates `scheduleReminders()`. Not in the original finding: a local
  notification surfacing 24h later ("You haven't added funds yet") is an
  install tell, and unlike localStorage residue it outlives the session that
  created it. `cancelReminders()` is deliberately left ungated — cancelling
  only removes state, and gating it would make a decoy session decline to
  cancel a real pending reminder, manufacturing the leak the gate exists to
  prevent.
- 15 tests, written before the fix and confirmed failing against the
  unmodified module (14 of 15 red; the 15th asserts cancel still works and
  passed both before and after). Each marker asserts no-residue under
  deniability, no-residue under demo, and that the real session can still fire
  afterwards — the last is what catches funnel theft, since a no-write
  assertion alone would pass even if the flag were consumed another way.

Egress gating is **not** duplicated by that PR; it stays at the single
chokepoint in `trackEvent.js`. The PR closes only what that chokepoint cannot
see.
