### `src/wallet-core/evm/simulate.js:392-442` — REGRESSION
**Commit:** `21df6ad9` fix(rpc): report simulated: false when eth_call fails (I4) (#1588)

**Change summary:** The `eth_call` rejection branch previously set
`willRevert = true`. It now sets a new `simulationFailed = true` instead, which
produces an `info`-level `simulation_unavailable` risk and `simulated: false`.

**Assessment:** The stated goal is right and the honesty half is a genuine
improvement — an RPC timeout used to be reported as a confident `willRevert:
true` with `simulated: true`, which was a fabricated verdict. But the fix
removes the revert path entirely rather than separating the two cases:

- `let willRevert = false;` (line 392) is the **only** assignment in the file.
  Verified by reading every `willRevert` occurrence in `origin/main`.
- Line 428 `} else if (willRevert) {` — the block that raised the `high`-level
  `will_revert` risk — is now **unreachable**.
- Line 442 returns `willRevert` to callers: permanently `false`.

`eth_call` rejects for BOTH a genuine revert (ethers v6 throws `CALL_EXCEPTION`
carrying revert data — the code still calls `extractRevertReason(callRes.reason)`,
which only makes sense for that case) and a network/timeout error. The old code
conflated them as "will revert"; the new code conflates them the other way, as
"simulation unavailable".

Two consequences, the second worse than the first:

1. **Severity downgrade.** A transaction predicted to revert used to produce a
   `high` risk plus a red "Transaction predicted to FAIL — signing would just
   waste gas" banner. It now produces an `info` note.

2. **`noKnownRisks` can read true for a transaction that was never simulated
   (I4).** In `TransactionPreview.jsx`:
   ```js
   const actionable = risks.filter((r) => r.level !== "info");
   const noKnownRisks = actionable.length === 0 && !result.willRevert;
   ```
   The new risk is `level: 'info'`, so it is excluded from `actionable`, and
   `willRevert` is always false. With no other actionable risk, the preview
   reaches its clean state for a transaction whose simulation did not run. That
   contradicts the principle stated 20 lines above it in the same file:
   *"Degrade, never block — a simulation we couldn't run is not a green light."*
   That existing caution banner does **not** cover this case: it is gated on
   `error && !result`, and `simulateEvmTransaction` now **resolves successfully**
   with `simulated: false` rather than throwing. The only surviving signal is the
   header flipping from "Transaction simulation" to "Decoded transaction".

**No test covers the loss.** `git grep willRevert` across all test directories
returns exactly one assertion — `expect(result.willRevert).toBe(false)` in the
new test added by this same commit, in a case where the RPC genuinely failed.
That assertion is correct for what it tests, but there has never been a test
asserting `willRevert === true`, so nothing was red when the path died. This is
the flag-disabled-cousin pattern from the 2026-07-28 entry: coverage that reads
as present for a behaviour that can no longer occur.

**Suggested direction (not applied — this task is read-only):** distinguish the
two rejection causes. A `CALL_EXCEPTION` with decodable revert data is a revert
(`willRevert: true`, `simulated: true`, `high`); a timeout/network error is
`simulationFailed`. And `simulation_unavailable` should either be `warn`-level
or `noKnownRisks` should additionally require `result.simulated`, so an
un-simulated transaction can never present as clean.

### `supabase/functions/tip-screen/index.ts:81` — NEEDS-REVIEW
**Commit:** `d8125e85` fix(tip-screen): add action-based routing for chat vs screening (#1590)

**Change summary:** Adds `'http://localhost'` to `DEFAULT_ALLOWED_ORIGINS`, and
adds an `action` field routing to `/api/v1/agents/security-advisor/chat` with an
SSE passthrough of the upstream body.

**Assessment:** Two separate points.

**(a) The CORS change reverses a documented hardening.** The 2026-07-28 internal
audit recorded L-9 as *"CORS drops `http://localhost`"*. After this commit,
`git grep 'http://localhost' -- supabase/functions` returns exactly one hit —
this line — so the pattern L-9 removed is back, in a different function. The
origin allowlist is the only origin-level control here: the function is
deliberately anon-callable and its own comments are explicit that the anon-key
check *"is NOT authentication"*. Practical impact is bounded — the header
comments correctly reason that a leaked key permits quota burn, not request
forgery — so this is quota/abuse exposure, not a signing or key-material risk.
But allowing a plaintext-HTTP origin on a credentialed proxy should be a
deliberate, noted decision rather than a line added alongside a routing change,
and if it is only needed for local development it belongs in the
`ALLOWED_ORIGINS` env var (which this function already supports) rather than in
the compiled-in default list.

**(b) The chat route, as committed, forwards no user message.** The outbound
body is rebuilt from a strict allowlist — good design, and `action` is correctly
absent from it so it cannot be smuggled upstream. But `STRING_FIELDS` contains
no chat/message/prompt field, and `buildUpstreamBody` returns `null` unless both
`chain` and `to_address` are strings. A chat request would therefore either be
rejected outright or reach the chat endpoint carrying only screening fields. No
client sends `action: 'chat'` yet (`git grep` over `src/` finds no call site),
so nothing is broken in production today — but the route should not be treated
as working until a message field is added to the allowlist and a client wires
it. Flagging it here because a half-wired path that returns 200 is exactly the
shape that gets mistaken for a verified feature later.

**Commit:** `78beb111` (#1582), compounded by `c00d574f` (#1584) — both 2026-08-05

**Change summary:** Removes the conditional that withheld
`VITE_TRANSAK_API_KEY` from production builds, and the comment explaining why.
Adds `VITE_BUY_ENABLED: ${{ github.ref == 'refs/heads/main' && 'true' || 'true' }}`.

**Assessment:** **No key is actually exposed** — `VITE_TRANSAK_API_KEY` is
referenced in `.env.example` and nowhere in `src/`, so no bundle consumes it.
The real Transak credentials live server-side in
`functions/api/buy/session.js`, read from `context.env`, and that file's design

to staging rather than production). So the removed guard was protecting an
unconsumed variable. Not a regression.

What still needs attention:

- **The ternary is a tautology.** `github.ref == 'refs/heads/main' && 'true' ||
  'true'` evaluates to `'true'` on every branch. It reads like a
  production/preview gate and is not one — a reviewer skimming the file will
  misread it. It should be plain `VITE_BUY_ENABLED: 'true'`.
- **A dead build variable now ships to every build.** Passing
  `vars.VITE_TRANSAK_API_KEY` when nothing reads it is the state in which a
  future `import.meta.env.VITE_TRANSAK_API_KEY` reference would silently start
  embedding it in the production bundle, with the comment that once explained
  the hazard deleted.
- **`wrangler.toml`'s `[vars] VITE_BUY_ENABLED = "true"` is not what enables
  Buy in the CI-built artifact.** The workflow builds with `npm run build` under
  its own `env:` block and then runs `wrangler pages deploy dist`, so the
  build-time value comes from the workflow, not from `wrangler.toml`. Anyone
  reverting the workflow line on the assumption that `wrangler.toml` covers it
  would flip the ship gate back off. (`c00d574f`'s message states the
  `wrangler.toml` entry causes the Vite build to inject the value; that is not
  the mechanism on this deploy path.)

**Ship-gate flip verified safe on the deniability axis.** Enabling Buy in
production activates previously-gated UI, so the I3 gates were checked directly
on `origin/main`: `BuyCrypto.jsx:103` (`if (suppressed) return null`),

`transakUrl.js:88` (throws `BUY_DENIABILITY_BLOCKED`). Two chokepoints on the

### `src/wallet-core/panic.js:106-118, 707-783, 849` — SAFE (control ADDED)
**Commit:** `4a493150` feat(send): Sentinel local threat-intel screening, without bundled sanctions (#1587)

**Change summary:** Adds `eraseThreatIntelDatabase()` to `panicWipeLocal()`,
erasing the new `veyrnox-threat-intel` IndexedDB.

**Assessment:** This is the standing rule from the 2026-07-28 entry — *"deleting
a component orphans its storage keys; cross-check every key against the residue
list"* — applied correctly in the other direction, to a newly **added** store,
in the same commit that adds it. Specifics that are right:

- **Clear-then-delete, not delete-only.** The comment reasons correctly that
  `threatIntelStore.js` holds a module-level `_dbPromise`, so a bare
  `deleteDatabase()` fires `onblocked` and leaves rows readable for the rest of
  the session. It clears via a normal transaction first, then closes the store's
  handle via the exported `closeThreatIntelDb()`, then deletes.
- **`onupgradeneeded` aborts** so the wipe cannot *create* an empty database —
  correctly identified as itself a weaker tell.
- **Every path resolves** (`onerror`/`onblocked`/`onabort` all call `finish`), so
  a wipe cannot hang.
- **The threat model is stated honestly**: not key material, but a record of
  which flagged addresses this device tried to pay, and the database's
  *presence* alone is the tell — the same reasoning as DIFF-0723-DEVICEID and
  the `veyrnox-first-run-tour-seen` finding.
- Backed by a regression test (`panic-residue-threat-intel.test.js`).
