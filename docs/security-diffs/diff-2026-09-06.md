## ⚠️ REGRESSION DETECTED

- `functions/api/bug-report/upload.js` accepts an arbitrary syntactically-valid
  report ID without proving that its database reservation exists, is still
  `reserved`, or has the declared size.  A deployed handler with its
  service-role configuration can therefore write arbitrary caller-supplied
  bytes to the private bucket.
- `sql/bug-report-upload.sql` creates an `ALL` storage policy without a role
  restriction.  The policy applies to `PUBLIC`, not only `service_role` as its
  comment claims, so it authorizes matching `bug-reports` objects for anon and
  authenticated roles when the migration is applied.

### functions/api/bug-report/upload.js:42 — REGRESSION
**Commit:** `694491f8` feat(bug-report): slice 1e-3 — server upload path (#2335)

**Change summary:** A new unauthenticated Pages endpoint validates headers and
uses `SUPABASE_SERVICE_ROLE_KEY` to write a caller-selected
`<uuid>.br1` object to Storage.  Its stated contract requires a preceding
`create_bug_report_upload` reservation, but the handler never reads
`bug_reports` before the Storage POST; its later PATCH is best-effort and can
also update zero rows.

**Assessment:** The UI flag does not gate a directly reachable Pages Function.
With the configured service-role environment, any caller can choose a fresh UUID
and upload up to 52 MiB, bypassing the intended per-device reservation and
database size/status checks.  The per-IP cache limiter is defence in depth only
(60/minute, non-atomic and per-colo), not the missing authorization control.
Static finding; whether this migration and environment are deployed was not
tested here.  Reject missing/non-reserved/mismatched rows before writing, and
make the update conditional on that same reservation.

### sql/bug-report-upload.sql:168 — REGRESSION
**Commit:** `c1cf8203` feat(bug-report): slice 1e-2 — Supabase schema for upload path (#2334)

**Change summary:** The migration enables RLS on the new private bucket's
objects, then defines `bug_reports_service_role_all` as `FOR ALL` with only a
`bucket_id = 'bug-reports'` predicate.

**Assessment:** PostgreSQL policies without `TO <role>` apply to `PUBLIC`.
The SQL comment saying the policy is service-role-only is therefore incorrect:
the predicate constrains the bucket, not the caller role.  If this migration is
applied, anon/authenticated callers with the normal Storage table grants can
read, list, insert, update, or delete matching private-bucket objects.  Replace
the policy with an explicit `TO service_role` policy (or remove it, since
`service_role` bypasses RLS) and verify the effective Storage grants/policies in
the target project.  Static finding; migration deployment was not tested here.
