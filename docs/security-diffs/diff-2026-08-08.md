### `src/components/SecurityAdvisor.jsx:54,448-455` — NEEDS-REVIEW
**Commit:** `0e06180d` (#1614)
**Change summary:** The Advisor's chat request moved from
`${SUPABASE_URL}/functions/v1/tip-screen` to
`${VITE_TIP_BASE_URL}/api/v1/chat`, and the request headers went from

```
{ "Content-Type", "apikey": ANON_KEY, "Authorization": Bearer ANON_KEY }
```

to `{ "Content-Type": "application/json" }` — no credential of any kind.

**Assessment:** The endpoint is now reachable by anyone who knows the URL, and
`tip.veyrnox.com` ships in the client bundle and in the `index.html` CSP, so
it is public knowledge. The commit is candid that the anon key was never
authentication, and it is right — but it *was* a filter against unkeyed
drive-by traffic, and removing it leaves the per-`device_id` cap (30 turns /
24h) as the only control on a Llama-3.1-8B inference endpoint that Veyrnox
pays for.

`device_id` is minted client-side by `getOrCreateDeviceId()` and sent in the
request body. Nothing binds it to anything. Rotating it per request is a
one-line change for a caller, so the cap bounds an honest client and no one
else. This is an uncapped third-party inference-cost vector, not a wallet-key
exposure — no I1/I2 consequence, and consent gating is correctly enforced at
the egress point (`sendMessage` checks `hasAdvisorConsent()` before any fetch,
verified at `SecurityAdvisor.jsx`). Rate limiting belongs on the Worker, keyed
on something the client does not choose.

### `src/wallet-core/evm/simulate.js:433,491` — NEEDS-REVIEW
**Commit:** `25fade75` fix(simulate): restore EVM revert prediction, keep the I4 honesty fix (#1597)
**Change summary:** Restores the `willRevert` assignment, which had been
missing entirely — the commit's own comment records that the branch was
"permanently false, its branch below unreachable". On the restored path,
`revertReason = extractRevertReason(callRes.reason)` is interpolated into a
`level: 'high'` risk detail and into `TransactionPreview.jsx:113`.

**Assessment:** `extractRevertReason` is
`e?.reason || e?.shortMessage || e?.info?.error?.message || e?.message || null`.
The third term is the raw JSON-RPC error message from the provider. It reaches
the signing UI with no length cap, no allowlist, no truncation — I checked both
render sites and neither bounds it.

The threat model is not hypothetical or mine; it is stated 40 lines above the
change, in the file's own words: a malicious RPC can *"inject an inflammatory
revertReason on a legitimate one"*. React escapes markup so there is no XSS,
but the injected value lands inside the highest-severity warning the preview
can show, which is exactly where a user is primed to act on text. A hostile or
compromised endpoint can render arbitrary prose — including instructions — in
the app's own voice, on the screen where someone is deciding whether to sign.

Attribution matters here: this is a **latent path this window activated**.
Before `25fade75`, `willRevert` was never true and neither render site could
fire. The commit is otherwise a genuine improvement (it fixes a real
three-valued-rejection bug and removes raw error text from the *degraded*
path, at `simulate.js:440-447`, explicitly citing CLAUDE.md A10). The
inconsistency is that the same reasoning was not applied to the revert branch
it was restoring. A cap and a decoded-reason-only rule would close it.

## Observation (pre-existing, not from this window)

`src/api/edgeApi.js:6` claims *"I3 CHOKEPOINT: every function checks
isDeniabilityOrDemoActive() before making a network call."* That is not true
and was not true before this window either: `fetchPrices`, `fetchKlines`,

and `GasTracker.jsx`, both of which compute `egressAllowed = i3Active && !DEMO`

documentation-accuracy item, not a live violation. It is worth correcting
anyway: a header asserting a chokepoint invites the next caller to skip a gate
that is actually enforced three files away. This is the same shape as the
two-chokepoint lesson recorded in CLAUDE.md for `lib/consent.js`.
