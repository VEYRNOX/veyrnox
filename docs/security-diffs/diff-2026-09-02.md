## ⚠️ REGRESSION DETECTED

### 1. `src/pages/Settings.jsx:89` — duress configuration is disclosed to the backend

`duress_configured: true` is published into the Security Advisor snapshot and
transmitted to the TIP chat backend alongside a **persistent** `device_id`. An
untrusted backend (I5) therefore learns that a specific device has a
duress/decoy wallet configured — which is the one fact the entire coercion-
resistance model depends on nobody being able to establish.

### 2. `src/pages/RestoreFromShares.jsx:16` — an audit control was relaxed against a compensating factor that is not enforced

The native shard-restore re-wrap credential drops from a ≥16-char passphrase to
an 8-digit PIN. The stated compensating factor — "hardware KEK re-enrolment is
MANDATORY before first sign" — does not exist as an enforced control, and the
claim is repeated in user-facing copy.

Both are detailed below.

## Flagged changes

### `src/pages/Settings.jsx:66-95` — **REGRESSION**
**Commit:** `c5d2524e feat(advisor): P1 Settings publisher (deniability pages skipped, see body)`

**Change summary:** Adds an advisor-context publisher to Settings emitting
`{ kek_enrolled, biometric_or_passkey, duress_configured, telemetry_consent,
safety_plus_active }`. Correctly suppressed to `null` in decoy / hidden /
deniability / locked sessions.

**Assessment:** The I3 gating is right and is not the problem — the leak is from
the **real** session. Traced end to end:

- `Settings.jsx:83-91` → `publishAdvisorContext({ settings: { duress_configured } })`
- `advisorBridge.js` → `CustomEvent(ADVISOR_CONTEXT_EVENT)` → `SecurityAdvisor.jsx:1108`
  `setLiveSnapshot(detail.context)`
- `SecurityAdvisor.jsx:1040` `effectivePageSnapshot = { ...pageSnapshot, ...liveSnapshot }`
- `SecurityAdvisor.jsx:1316-1327` → request body `context.page_snapshot = effectivePageSnapshot`,
  plus `device_id: getOrCreateDeviceId()` — the **persistent** id, not a per-session one
- `fetch(TIP_CHAT_URL, …)` → Supabase Edge `tip-chat` → Cloudflare Worker

So the wire carries, correlatable by device id: *this device has a duress wallet
configured.*

This is **not** an I2 violation — egress is gated on
`advisorOnlineEnabled && hasAdvisorConsent()` (`SecurityAdvisor.jsx:1168`), so it
is consented, not silent. It is a **coercion-resistance** regression. The threat
model that duress/decoy exists to defeat is an adversary who compels the user and
whose only counter is that the user can credibly claim there is nothing else on
the device. A backend record that the device *does* have duress configured
defeats that claim, and I5 says explicitly that the backend is untrusted. The
design-system rule "deniability by default (never show wallet count/list)" is the
same principle applied to the screen; this is the wire.

Consenting to an AI security advisor is not consent to disclose that you run a
duress wallet, so the existing consent gate does not cover this field.

**Narrowest fix:** drop `duress_configured` from the published payload. The
advisor cannot act on it usefully — every piece of advice it could give ("set up
a duress PIN") is derivable from the route the user is already on. The other four
fields in the same object (`kek_enrolled`, `biometric_or_passkey`,
`telemetry_consent`, `safety_plus_active`) are posture booleans that carry no
coercion-relevant information and can stay.

**Not verified:** no wire capture was taken. This is read from source across
five files; the transmission is a code path, not an observed request.

### `src/pages/RestoreFromShares.jsx:15-27, 157-215` — **REGRESSION**
**Commit:** `a10542ac feat(shard-restore): prompt fresh 8-digit PIN + trigger KEK re-enrol post-restore`

**Change summary:** On native, the credential that re-wraps a shard-restored
vault changes from `checkRecoveryPassphrase` (≥16 chars) to `/^\d{8}$/`. Web
keeps the passphrase. The just-typed PIN is handed to `WalletEntry` via router
state (`pendingKekEnrollPin`) so the KEK gate can auto-enrol.

**Assessment:** The *decision* carries owner sign-off, which the file records, and
the consistency argument is real — every other vault-entry path in the app (fresh
create, phrase import, PIN recovery, file restore) is already 8-digit PIN plus
KEK auto-enrol, so this brings shard restore to parity rather than inventing a
new weak path. That part is defensible.

What is not defensible is the compensating factor the file claims to rest on. The
2026-08-16 audit note it is overwriting says the passphrase must not be relaxed
"without owner sign-off **and a compensating factor** (hardware KEK re-enrolment
before first sign, …)". The replacement note asserts that factor is now in place:

> "on NATIVE the re-wrap credential is an 8-digit PIN and hardware KEK
> re-enrolment is **MANDATORY before first sign**."

It is not mandatory. Three checks, all against `origin/main`:

1. `KekEnrollmentGate.jsx:287-305` renders an **explicit Skip button**, whose own
   copy states the outcome honestly — *"If you skip, your wallet will be protected
   by your PIN only."*
2. `WalletEntry.jsx:809` `handleKekSkip` calls `kekDismiss()` and nothing else. The
   dismissal is in-memory; the gate re-fires next unlock, but the user reaches the
   wallet now.
3. `git grep -l isHardwareKekEnrolled -- src` returns `SecurityPosture.jsx`,
   `hardwareKekStatus.js`, `PersonalBackup.jsx` and two tests. **No signing path
   consults it** — not `SendCrypto.jsx`, not `CryptoSigning.jsx`, not
   `sign-gate/**`, not the WalletConnect chokepoints.

So a user can restore from shards, tap Skip, and sign immediately from a vault
sealed at ~27 bits with no hardware anchor. The file itself concedes the other
half — "hardware unavailable falls back to the same insecure tier path
fresh-create uses" — which is a second unenforced path to the same state.

The user-facing string carries the same false claim
(`RestoreFromShares.jsx:320`): *"you will be prompted to re-enable Hardware
Protection — that step is required before you can sign any transaction."* That is
a security guarantee the code does not implement, shown to the user at the moment
they are choosing the credential. Under the project's own "no fake security" rule
and I4, this is the finding — not the credential change itself.

**Two honest exits, both smaller than reverting the credential:**
- Make it true: gate the signing chokepoints on `isHardwareKekEnrolled()` for
  shard-restored vaults, or
- Make the copy true: say the prompt is strongly recommended and state what
  skipping costs, matching the wording `KekEnrollmentGate` already uses.

Reverting native to the passphrase is the third option but discards the owner
decision and the parity argument, so it is the worst of the three.

**Secondary, lower severity, same commit:** the PIN transits
`history.state` via `navigate("/", { state: { pendingKekEnrollPin } })`.
`WalletEntry.jsx:694` consumes it one-shot and replaces the entry with
`state: null` (this is what `92d7e08f` fixed — it preserves Router's own `idx`/key
bookkeeping rather than reaching for the raw history API, which is correct). The
exposure window is one render, and it is in-memory. Worth knowing it exists; not
worth changing on its own.

### `src/wallet-core/vaultBackup.js` (whole file) — **NEEDS-REVIEW**
**Commit:** `910c729a fix(backup): single combined seal (password + 8-digit PIN both required)`

**Change summary:** Replaces the two-seal envelope (`seals.password` OR
`seals.pin`, either alone sufficient) with one seal under
`combineBackupCredential(password, pin)` = `password + 0x1F + pin`. Export floors
move to ≥16-char password and exactly 8 digits. `BACKUP_VERSION` 1→2,
`BIN_VERSION` 2→3, `decryptPinSeal`/`decryptPasswordSeal` collapse into
`decryptBackupSeal`.

**Assessment — the crypto is right and is a clear improvement.** It closes the
2026-08-16 finding at the root: the PIN-only door that gave a ~10^8 offline
surface regardless of password strength is gone, rather than papered over by the
12-digit stopgap that broke PinPad parity. The domain separator holds — `pin` is
constrained to exactly 8 digits, so the last 9 characters of the combined secret
parse unambiguously and no two `(password, pin)` pairs collide, even if a pasted
password itself contained `0x1F`. Both credentials are now required, matching the
shard-export model.

**The open item is the removed read path.** `decodeBinary` now rejects anything
but `BIN_VERSION 3`, and `isValidBackup` requires `backup_v === 2`. The rationale
given is:

> "No production users existed at the time of the cut, so no legacy-envelope read
> path is retained."

That is true of App Store users and false of testers. `PersonalBackup` is routed
unconditionally (`App.jsx:212`), the Export tab is behind the Safety Plus tier
check only — no feature flag, nothing in `.env.production` gating it — so the
export path has been reachable in every TestFlight build from 1.0.1 (1) onward and
every Play internal versionCode. Any `.enc` a tester produced before today is now
unrestorable, permanently.

This is the same shape as the shard-bundle v1 window investigated yesterday
(#2220, corrected by #2223) — a "nothing shipped" premise that turned out to rest
on the wrong definition of shipped. Worth checking against that precedent before
accepting it a second time.

It **fails honest**, which is the mitigating half: an old binary envelope throws
`Unsupported backup version`, not a wrong-credentials error, so nobody is left
guessing at a password that would never have worked. Rated NEEDS-REVIEW rather
than REGRESSION for that reason.

**Owner call needed:** confirm whether any tester `.enc` exists. If one might,
either restore a read-only v1/v2 path (decrypt-and-migrate, no v1 writes) or
state the break explicitly in release notes.

Phase 1b's duplicate-symbol rows (USDC/USDT on 5 chains) were flipped on

- `sendWalletSource.js:133` `defaultAssetSymbol` maps ids → symbols and returns a

  USDC rows, the send route cannot tell which chain was picked.
- `balanceDisplay.js:51` `resolveAssetRow` falls back to
  `list.find(x => x.symbol === key)` — first match wins.
- `useReceiveDetector.js:100` writes `current[asset.symbol]` — two chains' balances
  collide on one key, last write wins, and a receive on the losing chain is not
  detected.
- `walletMeta.js:81` `sanitizeAssets` migrates a legacy bare `'USDC'` via
  `getAsset`, which `assets.js:159` documents as returning the **first** match —
  silently picking mainnet and dropping any other-chain preference.

`assets.js:157-160` already flags this in its own docstring ("Phase 1 may introduce
duplicates, at which point this returns the FIRST match and callers should migrate
to `getAssetById`"), so the hazard is known; it just has not been discharged.

**The risk is the ordering.** Re-landing Phase 1b flips four latent
first-match bugs live at once, one of them (`defaultAssetSymbol`) on the send
path. Fix the four call sites *before* the rows come back, not in the same PR —
a wrong-chain default on a send picker is a funds-loss shape.

## Correction (2026-09-02, post-merge — checkpoint 3)

Verified against `origin/main` at `ba5dbe7b` (2026-09-02T14:57:00Z), after this
report's own PR (#2255) merged. Three commits landed between window close
(`62b19bb6`) and that tip: `5f1897a9` (#2253, covered at checkpoint 2), this
report (#2255), and:

> `74742f47 fix(assets): getAsset resolves composite id or bare symbol (Phase 1a follow-up) (#2254)`

It bears on the Phase 1a finding above. It **does not resolve it**, and reading
its diff turned up two things worth recording — one against that commit, one
against this report.

### What it changed

`getAsset` goes from `ASSETS.find(a => a.symbol === key)` to
`ASSETS.find(a => a.id === key) || ASSETS.find(a => a.symbol === key)` — id
first, symbol fallback. One file, one function.

### It does not close the finding — and it removed the warning

The finding is that readers collapse composite ids back to bare symbols, and
that Phase 1b's duplicate-symbol rows will make first-match resolution wrong. An
id-then-symbol fallback preserves exactly that first-match behaviour, so the
hazard is unchanged.

What *did* change is its visibility. The docstring `74742f47` deleted was the one
this report cited as evidence the hazard was already known:

> "Phase 1 may introduce duplicates, at which point this returns the FIRST match
> and callers should migrate to `getAssetById`"

Its replacement drops that sentence. So the in-code warning against re-landing
Phase 1b without first fixing the four call sites is gone, which makes the
finding *less* discoverable rather than more. The four call sites named above
(`defaultAssetSymbol`, `resolveAssetRow`, `useReceiveDetector`, `sanitizeAssets`)
are untouched and the item stands.

### Its stated premise does not match the code it landed on

`74742f47`'s message says four consumers "still call `getAsset(sym)` with
whatever the store holds", so "on any migrated wallet those calls returned
null — the picker hid the asset, the detector skipped it, the balance dropped,
and the analytics event never emitted."

Checked all four at both `62b19bb6` (window close) and `5f1897a9` (that commit's
actual parent). All four already resolved composite ids:

| file | at `5f1897a9` |
|---|---|
| `WalletAssetPickerSheet.jsx:55` | `getAssetById(id)` |
| `useReceiveDetector.js:90,97` | `getAssetById(entry) \|\| (!isAssetIdString(entry) ? getAsset(entry) : null)` |
| `portfolioBalances.js:145` | same pattern |
| `useAnalytics.js:41` | same pattern |

None could have returned null on a composite id. Those consumers were migrated
earlier in the same window by `251c144b` (Phase 1a) and `d9127147` (the picker
fix), both inside this report's scan range.

This is not a claim that the change is harmful — an id-or-symbol `getAsset` is
defensible as defence in depth, and the added `assets.compositeId.test`
regression is real. It is a note that the **breakage it describes was already
fixed**, so the message overstates what it repaired, and a future reader tracing
"when did the Send picker break" from that message will be sent to the wrong
window. Same class as the staleness events recorded in `CLAUDE.md`: a statement
true of an earlier tree, written as though true of the current one.

### What this report got wrong

Nothing above excuses the miss on this side. This report rated the Phase 1a
migration NEEDS-REVIEW purely for the *latent* duplicate-symbol hazard and
described the readers as safe today. That was right about the four files it
examined, but the scan never diffed
`src/components/send/WalletAssetPickerSheet.jsx` — it appears in the changed-file
list, was filed under money-movement UI, and was then only skimmed. Had
`d9127147` not already fixed it, an asset silently missing from the **Send**
picker would have been a live defect inside the window and this scan would have
reported clean on it.

The lesson is the runbook's own rule, unheeded: a file that reaches the flagged
list gets the diff, not a category.

Findings 1–5 all stand. Nothing in the post-merge window resolved any of them.
