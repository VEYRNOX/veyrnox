*presence* proves a real Veyrnox install existed — explicitly for keys that are
not key material and are never read again. `veyrnox-kek-pin-notice`,
`veyrnox-live-prices`, `veyrnox-2fa-biometric-auto` and the whole PR #1344
telemetry-marker block are all in the list on exactly that basis, and the #1344
comment names the failure mode this reproduces: *"Without these,
inspectKeyMaterial() reported clean:true while they sat in storage, so the
post-wipe 'nothing recoverable remains' claim was overstated."*

`veyrnox-first-run-tour-seen` is the same class — it proves a real Veyrnox
install existed on this device and completed a security-feature walkthrough.

Exposure is real but narrow: the tour shipped in PR #1174 (`aca998a2`,
2026-07-18) and was deleted 2026-07-27, so only devices that ran a build from
that ~9-day span carry the keys — which includes the Play internal-testing track
(live 2026-07-22). No key material, no addresses, no amounts.

Suggested resolution (source change — **out of scope for this task, not
applied**): add both key strings to `METADATA_RESIDUE_KEYS` in

`docs/Feature-Status.md`. That is a wipe-completeness change only — it touches

### `.github/workflows/deploy-preview.yml` — SAFE
**Commit:** `4766b4b0` ci(deploy): skip staging deploy/e2e on docs-only PRs
**Change summary:** New `changes` job computes `docs_only` from the PR diff; the
`deploy` job gains `needs.changes.outputs.docs_only != 'true'`; `staging-gate`
passes when *both* `docs_only == true` and `deploy == skipped`.

**Assessment:** Reviewed as a potential fail-open, and it is not one.
- The filter is an **allowlist** (`^docs/`, `^\.github/ISSUE_TEMPLATE/`,
  `^\.github/PULL_REQUEST_TEMPLATE`, `\.md$`, `^LICENSE$`) — every changed file
  must match or the full pipeline runs. `package.json`, `package-lock.json`,
  `src/`, `scripts/`, `android/`, `ios/`, and `.github/workflows/` are all
  non-exempt.
- Every failure path (`event != pull_request`, missing sha, `git diff` failure,
  empty diff) calls `run_everything` and sets `docs_only=false`. I4 holds.
- The `deploy` gate uses `!= 'true'` rather than `== 'false'`, so an empty
  output from a failed `changes` job keeps deploying. An exemption must be
  affirmatively earned.
- `staging-gate` keeps `if: always()` and no path filter of its own — correct,
  since it is a required status check and a required check that never runs
  blocks the merge forever rather than being treated as skipped.
- Adversarial input: a filename containing a newline is emitted by git as a
  single quoted path beginning with `"`, which matches no allowlist pattern and
  therefore forces the full pipeline. Fails closed.

Note for future edits: `\.md$` is unanchored to a directory, so it exempts

### `src/lib/tracking-integration.jsx` — SAFE (control ADDED, I3)
**Commit:** `0295898a` fix(i3,tracking): stop decoy sessions writing funnel state to shared storage (#1399)
**Change summary:** Adds `suppressed() = DEMO || isDeniabilityOrDemoActive()`
and applies it to `fireOnce()` (before the read, not just the write), to
`useFirstInbound`'s in-memory memo, and to `scheduleReminders()`.
`cancelReminders()` is deliberately NOT gated. `useFirstInbound`'s hand-rolled
localStorage dance is folded into `fireOnce()`.

**Assessment:** This closes a genuine I3 gap that the previous comment in this
file mis-attributed: `emit()`'s guards suppress *egress*, and this module writes
*local state* egress gating cannot see. `WalletPortfolioPage` and `SendCrypto`
both render in decoy/duress sessions with `isUnlocked` true, so before this
change a coerced session wrote once-per-install markers, the holdout bucket, and
scheduled local notifications into storage the real session shares. Two distinct
harms, both closed: residue (`veyrnox-first-inbound-fired` asserts funds were
once received) and funnel theft (the decoy burns the flag, so the real session's
milestone can never fire).

Verified every localStorage write in the module now routes through `fireOnce()`;
`assignHoldout()` is called inside a `fireOnce` callback and is therefore
covered. Gating the check *before* the read is what makes the decoy cost the
real session nothing. Leaving `cancelReminders()` ungated is correct and worth
preserving: cancelling only removes pending state, and gating it would let a
decoy session decline to cancel a reminder the real session scheduled — the
gate would manufacture the exact leak it exists to prevent.

One deliberate residual, unchanged and acceptable: `fireOnce`'s `catch` fires the
event anyway when localStorage is unavailable (over-count rather than lose). In a
suppressed session this is unreachable, because `isDeniabilityOrDemoActive()`
returns `true` on a throwing read before that point.
