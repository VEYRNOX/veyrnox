### src/lib/WalletProvider.jsx:206,555-590,1750-1762,2054 — NEEDS-REVIEW
**Commit:** `2971adac` Speed up native relock unlock flow (#1989)
**Change summary:** Adds `NATIVE_RELOCK_CACHE_MS = 30_000`. On native, `lock()`
now calls `armRecentNativeUnlockCache()`, which stores `{ secret: <plaintext
PIN/password>, payload: mv.serializeContainer(containerRef.current) }` in a
module ref for 30 seconds. A subsequent `unlock()` with a byte-equal secret
short-circuits to that payload.

**Assessment.** Three separate properties change, and each deserves its own line:

1. **`lock()`'s seed zeroization is defeated for the cache lifetime.**
   `armRecentNativeUnlockCache()` runs *before* the existing
   "best-effort overwrite of EVERY seed before dropping the container" loop, and
   `serializeContainer()` (`multiVault.js:280`) returns a JSON **string**
   containing `mnemonic` for every wallet, plus `actionPassword` when configured.
   So the deliberate wipe now runs against the original while a full plaintext
   copy survives it. Both the copy and the cached secret are JS strings, so
   `clearRecentNativeUnlockCache()` can only drop the reference — it cannot zero
   them; reclamation is at GC's discretion. Net effect on native: for 30s after
   every lock (idle, background, manual), every seed on the device is recoverable
   from the JS heap. That directly weakens the post-lock posture the
   coercion-resistance model rests on.

2. **The cache-hit path skips the biometric gate and the hardware KEK factor.**
   On a hit, `mnemonic = recentNativeUnlock.payload` replaces the whole `else`
   branch — so `keyStore.unlock()` is never called, and with it neither
   `getHardwareFactor` (Secure Enclave / StrongBox) nor the native
   `requireBiometric` gate. Inside the window, the PIN alone re-opens the wallet;
   I6's `KEK = HKDF(H ‖ C)` is not exercised because no unwrap happens at all.

3. **Within the window, a correct secret is instantly distinguishable.**
   A hit costs zero KDFs; a miss costs a full Argon2id. That is the H-1 oracle in
   its starkest form, for 30 seconds after each lock.

**What is correctly handled** (verified, not assumed): `panicWipe` and
`discardIncompleteWallet` both call `clearRecentNativeUnlockCache({
clearSessionSecret: true })` *before* `lock()`, and nulling
`sessionUnlockSecretRef` is what stops `lock()` re-arming the cache on its way
out — the `typeof … !== 'string'` guard in `armRecentNativeUnlockCache` is
load-bearing and correct. Decoy/hidden sessions are excluded at arm time. The
unmount effect clears it. A duress PIN cannot hit the cache (exact-match on the
secret). None of that is in question; the exposure above is what remains after
all of it works as designed.

**Recommendation:** owner ruling on whether 30s is the intended figure, and
whether the cached payload should be the *ciphertext* + a derived DEK handle
rather than the serialized plaintext container — the latter would keep most of
the latency win while leaving `lock()`'s zeroization meaningful.
