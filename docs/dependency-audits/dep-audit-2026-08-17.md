## Moderate / Low (summary)

All 18 low findings resolve to **one advisory**, unchanged from 2026-08-15:
[GHSA-848j-6mx2-7j84](https://github.com/advisories/GHSA-848j-6mx2-7j84) — *Elliptic Uses a
Cryptographic Primitive with a Risky Implementation*, `elliptic <=6.6.1` (installed:
6.6.1 — i.e. the latest release is itself still vulnerable). Reached by two independent
chains, both from **production** dependencies:

- **Ledger chain (direct dep `@ledgerhq/hw-app-eth`)** — `@ethersproject/signing-key` →
  `elliptic`, i.e. ethers **v5** vendored inside the Ledger SDK. Also drags
  `@ethersproject/{abi,abstract-provider,abstract-signer,hash,transactions}` and
  `@ledgerhq/evm-tools` into the report. npm's proposed fix is
  `@ledgerhq/hw-app-eth@6.40.3` — a **major downgrade** from the installed 7.8.12; declined.
- **Trezor chain (direct dep `@trezor/connect-web`)** — `@trezor/utxo-lib` →
  `tiny-secp256k1` → `elliptic`, plus `crypto-browserify` / `browserify-sign` /
  `create-ecdh`. npm reports `fixAvailable: false` — no upgrade path exists today.

Both chains are imported from `src/` (13 files reference `@trezor/connect-web` or
`@ledgerhq/hw-app-eth`; e.g. `src/wallet-core/hw/trezor.js`, `src/wallet-core/btc/hw-send.js`,
`src/wallet-core/sol/hw-send.js`), so this is production dependency surface, not dev-only.

**Honest scoping:** `elliptic` sits inside hardware-wallet vendor code, on a path that can
touch signature handling for Ledger/Trezor flows. Veyrnox's own key derivation and signing
use `@noble`/`@scure` exclusively and are not affected. The advisory is rated *low* and
concerns implementation risk in the primitive rather than a demonstrated key-recovery
exploit; no exploitability assessment against these specific call paths has been done here.
Tracking it as vendor-supply-chain exposure is the correct framing — not as a Veyrnox
crypto defect, and not as "clean" either.

Also note the hardware-wallet threat model limits the blast radius by design: the private
key never leaves the device, and signing happens on-device. `elliptic` in the host-side JS
is used for encoding/verification helpers, not for holding the user's key.

## Recommended actions

0. **Do not run `npm audit fix`.** Proven above to resolve 0 of 32 while performing ~378
   package operations and dropping the `appium` e2e toolchain. Not `--force` either.
1. **`uuid` / `xcode` / `@capacitor/cli` (moderate, CVSS 7.5) — candidate `overrides` pin,
   needs a human.** The automated fix does not reach it. The repo's established mechanism
   for exactly this shape is an `overrides` entry in `package.json`, and **two `uuid` pins
   of this exact form already exist**:

   ```json
   "@ledgerhq/client-ids": { "uuid": "^11.1.1" },
   "jayson":               { "uuid": "^11.1.1" }
   ```

   Adding `"xcode": { "uuid": "^11.1.1" }` would follow that precedent and clear all three
   moderate findings with a surgical lock diff.

   **Unverified caveat, stated plainly:** `xcode@3.0.1` declares `uuid: ^7.0.3`, so this
   forces a **four-major** jump, and npm nests 7.0.3 under `xcode` today precisely because
   the ranges do not overlap. Whether `xcode` only uses APIs that survive v7 → v11 was
   **not** determined by this run — `node_modules/xcode/` is empty in this checkout, so the
   source could not be inspected. Anyone taking this on should read `xcode`'s `uuid` call
   sites first and confirm `npx cap sync ios` still produces a valid `.pbxproj`. Do not
   land it blind on the strength of the two existing precedents.
2. **`deepmerge-ts` / `@wdio/*` (11 high) — decline, re-check weekly.** Do not downgrade to
   the 7.40.x line. Watch for a `deepmerge-ts@>=8` uptake in `@wdio/utils`; that is the
   forward exit, and it arrives on WebdriverIO's schedule, not ours. Note `npm audit fix`
   offers only 7.1.5 → 7.1.6, which stays inside the vulnerable range.
3. **`elliptic` (18 low) — no action available; keep tracking.** Unchanged for a second
   consecutive week. Both proposed remedies are major downgrades of hardware-wallet SDKs
   and are declined. `package.json` already carries an `"elliptic": "^6.6.1"` override,
   which pins the tree to the newest release — that release is itself still within the
   advisory range, so the override buys consistency, not remediation. Revisit if `elliptic`
   ships a patched version or if Trezor/Ledger move off it.
4. **`@noble`/`@scure` majors — leave pinned.** Zero advisories. Moving to 2.x is a
   deliberate, reviewed change under H-4 / CODEOWNERS, not a security response.
5. **`@ledgerhq/hw-app-eth` 7.8.12 → 7.8.14** — routine patch, does not clear any finding.
   Bundle into ordinary maintenance, not a security PR.
6. **Local `node_modules` is behind `package-lock.json`** on this machine. Run `npm ci`
   before drawing conclusions from `npm outdated` here again.

### Why no fix PR was opened by this run

The runbook escalates to an automatic `npm audit fix` PR only when a **CRITICAL or HIGH**
CVE affects `@noble/*`, `@scure/*`, `ethers`, or `@walletconnect/*`. That condition is not
met: every HIGH this week is in the `@wdio/*` devDependency tree, and the packages on that
watchlist carry no open CVE at their installed versions. The `uuid` cluster is *moderate*
and sits in `@capacitor/cli`, so it falls outside the automatic trigger — it is recommended
above for a human-reviewed PR rather than opened here, consistent with the rule that a
lockfile change never rides along with a docs report.

Independently of that gate, there was **nothing for a fix PR to contain**: the dry-run
shows `npm audit fix` resolves none of the 32 findings. The one remedy worth pursuing (the
`xcode`/`uuid` override) is a hand-written `package.json` edit with an unverified
compatibility risk, which is exactly the kind of change this task must not land
unattended.
